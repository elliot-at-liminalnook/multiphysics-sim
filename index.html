Planning doc — v0.21

A pluggable multi-domain physics simulator.

Models run through the generic equation compiler and integrator. Start with the project guide, the CAD-to-simulation acceptance example, or the phenomena gallery. Specialized actuator, leg and quadruped runtimes have been retired.

What we're building

A simulation core where every physics domain — rigid body, thermal, fluid, electrical, whatever comes later — is an independently authored plugin. Domains never reach into each other; behaviors meet either at typed acausal connectors or at explicitly directed causal signals. An acausal connector carries an across variable and a conserved through variable, and the compiler works out computational causality. Each connector kind defines its own units, compatibility rule and energy accounting rather than pretending every pair has the same physical product.

The model is data, not code — authored while the simulation runs, from a canvas or a script. A subsystem is anything that honors its ports: a nested graph, a reduced surrogate standing in for a thousand nodes, or firmware we didn't write — as source, as WASM, or as a binary running on an emulated chip. Fidelity is a runtime dial rather than an architectural commitment.

One vocabulary rule keeps the layers straight. An object is the persistent physical or CAD identity a user selects. A behavior is a registered equation or block implementation attached to an object. A port belongs to a behavior, and state belongs to stable state ids. “Component” remains informal prose for a user-facing block, never an implementation identity.

The bar is emergence. Perturb one edge of a rigorous system and behavior nobody encoded should fall out — a pendulum that stands upright when you shake it, a tube that sings when you heat it — so the acceptance suite is a list of documented surprises, checked by assertions that span domains in a single statement.

Bevy's ECS is the substrate: one semantic object may carry behaviors from any mix of domains at once — a resistor is an electrical element, a heat source and a lump of mass without becoming three visible objects — while each behavior, port and state value keeps its own stable identity. A resistor is three things at once below is what that buys. The core stays usable headless, and the scene is strictly a view of committed state, never an input to it. That one-way rule is what lets a gear you can watch turn be the same object the solver and tests refer to.

Detail on demand

The case worth designing for: a full circuit board solved honestly — extracted parasitics, hundreds of nodes, switching transients — and then handed to the rest of the system as a box with five ports. Both are the same board. The detailed model is the truth; the reduced one is what the enclosure, the fan, and the battery actually talk to.

Nothing about that is specific to boards. It's the general move: solve a subsystem at the resolution its physics demands, then expose a cheap surface that preserves whatever the outside world can observe. A gearbox, a battery pack, a hydraulic manifold — same shape.

  • Nanoseconds Traces and packages.

    An extracted RLC network with thousands of nodes. Where signal integrity and switching losses actually live.

  • Microseconds Functional blocks.

    Regulator, MCU, driver stage. Behavioral models with the transients averaged out but the control loops intact.

  • Milliseconds The board as one component.

    Power in, a handful of signal ports, one thermal port radiating total dissipation as a function of load.

  • Minutes The board in its enclosure.

    A heat source next to a fan curve and a chassis. Nothing at this level knows what a trace is.

Every rung is a legitimate model of the same object, and which one you want depends entirely on the question you're asking. So fidelity should be a runtime dial, not an architectural commitment.

A subsystem is just a component

A model containing a graph exposes ports exactly like a primitive does, and nothing outside can tell the difference. That one rule buys the whole hierarchy — boards nest in enclosures nest in vehicles, with no special case at any level.

Three ways to get the reduced model

Hand-authored surrogates, validated against the detailed run. Automatic order reduction — linearize around an operating point, then balanced truncation or moment matching, which is the well-trodden path for interconnect. Or fit a small state-space to simulation data. All three end at the same place: something that honors the port contract for less money.

Validity envelopes

A reduced model is only true somewhere — a frequency band, a load range, a temperature window. That envelope is declared as part of the model and checked while it runs, so leaving it is an event you can see rather than a wrong answer you can't.

Adaptive fidelity

You pay for detail only where you're looking. The board runs as an RLC network while you're debugging a gate driver and as a three-parameter thermal box while you're tuning the fan curve — swapped at runtime, with state handed across. Timescale separation is exactly what makes the coupled system tractable at all.

Zoom is a real operation

A reduced model keeps a link to what it was derived from, so opening the box on the canvas shows the network underneath — and changing that network marks the surrogate stale and offers to re-derive it. Provenance is what keeps the two from silently drifting apart.

Proposed architecture

Domain plugins

Each independently authored domain registers stable behavior descriptors: schemas, state layout, port declarations, residual builders, Jacobian strategy and serialization hooks. A small adapter may also register Bevy authoring and visualization systems, but physics domains never advance themselves through the Bevy schedule; the compiled runtime owns stepping.

Coupling layer

Cross-domain exchange goes through typed connectors rather than hand-wired reads and writes. A behavior that genuinely couples domains — a DC motor, electro-thermal resistor or mount — explicitly owns ports of several kinds and the constitutive equations between them. Domains remain independent because the bridge behavior, not either neighbouring domain, owns the coupling.

Black boxes at the boundary

Not every domain flattens into equations — a contact solver or a grid fluid solves internally however it likes. Such a block publishes a discrete-time multiport relation for the coupling step, normally f = Y·a + b: a full boundary Jacobian plus an offset, including cross-port effects and the block's history. A rollback-capable nonlinear block may answer pure residual queries iteratively; a non-rewindable block receives one pre-agreed fixed coupling step and advances exactly once after acceptance. The same transactional block seam later hosts foreign firmware.

Solver scheduling

One scheduler owns a fixed coupling timeline. The compiler groups states and algebraic constraints into strongly connected coupling islands; each island advances atomically with one integration policy. Opaque blocks may substep internally, and sampled causal blocks update only at declared event times. General adaptive and multirate coupling wait until rollback and error semantics are proven.

Integrators as a library

Verlet, implicit midpoint, BDF and friends live in the core as reusable pieces, but the choice belongs to a compiled coupling island rather than to each domain independently. A flattened electro-mechanical loop must take one coherent step; a self-contained opaque thermal or fluid block may use a different internal method behind its accepted boundary contract.

What a step actually is

Worth laying out plainly, because the rest of this document leans on it and none of it explains itself. A physics model does not tell you the future. It tells you rates. Newton gives you an acceleration, not a position. A thermal mass gives you a rate of temperature change, not a temperature. A capacitor tells you how fast its voltage is moving. Wire a hundred such components together and you still have nothing but a very well-informed description of the present instant.

An integrator turns rates into futures, and it is the only reason a continuous model moves at all. Everything else on this page — connectors, plugins, foreign blocks, index reduction — assembles honest residuals and constraints for a coupling island. The runtime schedules those islands and discrete events against one committed timeline. Strip the vocabulary away and the first implementation is this fixed-step transaction:

loop {                                      // one fixed coupling step
  trial.reset_from(&committed);             // nothing authoritative mutates
  apply_due_events(t, &mut trial);          // controllers mutate trial state once
  solve_coupling_islands(t, h, &committed, &mut trial)?;
  commit_step(h, trial, &mut committed)?;   // includes each opaque block once
  t += h;
}

The committed StateStore is the registry of all mutable state. Core-visible scalars and arrays live there directly under stable ids; an opaque block registers a BlockStateId whose private bytes remain behind its declared snapshot and commit capabilities. Compiled islands are disposable dense views. Failed solves discard trial state. Rollback-capable participants commit atomically; a non-rewindable block creates an irreversible barrier, and failure after crossing it terminates the run.

Why it isn't just rate × time

It can be — that's forward Euler, a real integrator and the worst one. The trouble is that the rate itself changes during the step, so multiplying the rate at the start by the whole interval is wrong by however much the rate moved in between. Every integrator is a different strategy for guessing what happened inside the step: sample the rate at several points and average them cleverly, solve for a rate that's consistent with where you land, or use a formula chosen to preserve something you care about rather than to minimize the error.

Step size is the whole economy

Halve the step and you roughly double the cost while usually reducing discretization error substantially. The first implementation chooses a fixed coupling step that lands exactly on controller events, which makes scheduling and non-rewindable blocks honest. Adaptive stepping comes later for islands where every participant can snapshot or roll back; trial evaluation remains pure and side effects remain deferred in either mode.

Our models are DAEs, not ODEs

A connector doesn't contribute a rate. “Across values agree” and “signed through values sum to zero” are algebraic truths with no derivative in them. Mixing those with rate equations gives a differential-algebraic system, which is why the compile pipeline has an index-reduction stage. State cannot be set arbitrarily; it must satisfy constraints at t = 0 and again at the seam after structural edits.

Stiffness is why there's more than one answer

A model is stiff when its fastest behavior and its slowest behavior are far apart in timescale — a switching transient measured in nanoseconds sitting next to a heatsink that takes minutes. An explicit integrator may need steps sized for the fast mode even after that mode has become uninteresting. Suitable implicit methods have much larger stability regions, though they still need adequate nonlinear solves, error control and a method appropriate to the problem.

What conservation has to do with any of it

An integrator that quietly leaks energy can be indistinguishable from friction we forgot to write down. That's tolerable in some dissipative studies and fatal for acceptance phenomena that live in small residual effects. Conservative islands therefore report energy drift, while every connector kind reports its own signed transfer balance; dissipative behaviors separately report accounted loss.

Which brings us to the three families, and the reason the choice is made per compiled coupling island rather than globally or independently per domain.

Explicit

Forward Euler, RK4. Take the current state and evaluate forward. Cheap and simple, but not generally structure-preserving: depending on the method, step and system, long oscillatory runs may gain or lose energy. Explicit stability limits can also make stiff systems prohibitively expensive.

Implicit

Backward Euler, BDF. Solve for a state consistent with its own derivative — usually a Newton iteration and a Jacobian inside every step. Much more work per step, but the right method can remain stable where an explicit scheme fails. Many implicit formulas introduce numerical damping, useful for stiff dissipative systems and potentially damaging for conservative oscillation, so the method still has to match the island.

Symplectic

Velocity Verlet, implicit midpoint. Built to preserve the geometric structure of a mechanical system rather than to minimize per-step error. Energy wobbles a little each step but doesn't drift — after a million steps the orbit is still an orbit. The catch is that "structure" means something specific: they apply cleanly to Hamiltonian mechanics, want care around constraints and contact, and don't generalize to an arbitrary DAE.

So there's no global winner. Velocity Verlet suits some unconstrained mechanical islands; implicit midpoint is a useful first choice for the constrained electro-mechanical slice; BDF-family methods suit many stiff dissipative islands. None is unconditionally accurate merely because it is stable, so step convergence and connector-specific energy diagnostics remain acceptance tests. Integrators live in the core while compiled island capabilities determine the choice.

Modelica, but you can see it

The idea Modelica gets right is the acausal connector. A behavior declares ports; each port carries an across variable and a conserved through variable. Wiring compatible ports together asserts that across values agree and signed through values sum to zero. You never declare an input side and an output side; structural analysis works out how the assembled equations can be solved.

That single rule is what makes multi-domain coupling uniform — every domain is the same shape, only the units change:

Rotational

angle · torque

Electrical

voltage · current

Thermal

temperature · heat flow

Hydraulic

pressure · volume flow

The algebra is uniform; the energetics are connector-specific. Electrical power is voltage times current, rotational power is angular velocity times torque, hydraulic power for the first incompressible model is pressure times volume flow, and thermal energy transfer is already the signed heat-flow rate. A connector kind defines that diagnostic explicitly. A bridge behavior may own one port of each relevant kind — a motor bridges electrical and rotational, a resistor bridges electrical and thermal — without either domain reading the other's state.

The graph is the source of truth

Components and connections live in a runtime graph, not in compiled code. Editing it is an ordinary mutation, so the visual canvas, a script, and a loaded model file are all just three ways of writing to the same structure.

Incremental recompile

Changing the model extracts a new immutable snapshot and re-runs flattening, matching, island partitioning and index reduction. Stable ids identify affected algebraic neighbourhoods, so only dirty coupling islands rebuild. Incremental compilation is a memoized form of the same pure pipeline, not a second compiler.

Visible by default

Where Modelica's tooling goes opaque, we stay legible: live values on connections, signed through direction animated, residuals and solver iterations shown per behavior, and flattened equations viewable for any selected object or port. Debugging a stiff model should be a matter of looking at it.

Scripting for what graphs are bad at

An embedded language — Rhai, settled below — covers the cases a canvas handles poorly: parameter sweeps, procedurally generated topologies, controllers, and test scenarios. Same API surface the editor uses: spawn, connect, set_param, step. Scripts can also define new component equations at runtime, which is how a user adds physics we never shipped.

Editing a running model without corrupting it

Settled: stable state ids survive when their owning behaviors survive an edit, only affected coupling islands re-initialize, and a pause-on-structural-change toggle exists for a failed seam solve. This feature is likely to corrupt a run quietly unless identity and transaction boundaries remain explicit.

State has stable identity outside the compiled solver. The authoritative StateStore is an ECS resource keyed by stable numeric and opaque-block state ids. Behaviors own handles into it; compiled unknown vectors, Jacobian sparsity and block ordering are disposable dense views. Recompilation remaps surviving ids rather than performing surgery on an authoritative solver array.

Stable identity, not position. Objects, behaviors, ports and state each receive generational ids independent of graph location or compiled array indices. Edits are named commands against those ids rather than diffs between anonymous graph states, so recompilation knows exactly what survived.

Only dirty coupling islands rebuild. Mark edited behaviors, extend that set through shared algebraic constraints, and rebuild affected islands alone. Stable state ids carry committed values forward; initialization runs only for new or invalidated state.

The genuinely hard part is consistent initialization. A DAE can't start from arbitrary values — algebraic variables have to satisfy their constraints at the restart instant, and the new subsystem has to be consistent with the state of everything around it that survived. So there's a small solve at the seam after every structural edit. It usually converges immediately and occasionally doesn't, and that moment is exactly what the pause toggle is for.

The edit log is the provenance. Every structural change is an entry: what changed, at what simulation time, and what it was derived from. That log is what marks a surrogate stale when its detailed model is edited, what lets zoom in find the right source, and what makes a whole session reproducible from a starting model plus a list of operations.

Undo is a snapshot, not an inverse. We already need whole-model snapshot and restore for foreign blocks, so an edit takes a checkpoint first and undo restores rather than trying to invert the operation. That matters because re-initialization isn't invertible — you cannot un-solve a seam.

A motor that spins a gear you can see

This is the reconciliation the whole thing lives or dies on, and it deserves a straight answer. A connector graph is a diagram. A motor driving a gearbox driving a load is five components and about nine equations, and not one of them mentions a shape, a position, or a direction in space. But the thing anyone actually wants on screen is a gear turning — and turning at the right speed, slowing when the load bites, stopping when the supply browns out.

The trap is to let those two pictures become two models. Once the renderer owns a transform that the physics also owns, they drift, and every bug afterwards is an argument about which one was right. So the answer is three layers with a strict rule about which way information flows: state is the only truth, and the scene reads from it and never writes back.

Drivetrains are one-dimensional, and that's not a compromise

A rotational port carries shaft angle as its across variable and torque as its through variable; angular velocity is the angle's derivative and power is ω·τ. Motor, shaft, gearbox, inertia, load: one or two equations each. A gear ratio is φ₁ = n·φ₂ and τ₂ = −n·τ₁. The gear you're watching spin has exactly one configuration state behind it.

The scene is a projection of state

Every object may declare a visual: a mesh, a fixed local offset and a binding from stable state ids to transform. For the gear that binding is “rotate about the mount axis by φ.” A Bevy projection system reads the committed StateStore after each step and writes disposable transforms; physics never reads them back.

Consequence: the visual can be wrong without the simulation being wrong, which is the right failure mode. Get the mesh offset backwards and you see a gear in the wrong place, not a machine with different physics.

Mounts are where 1D meets 3D

The bridge behavior people forget. A mount has a 1D flange on one side and a 3D frame on the other, plus an axis: it applies flange torque to the body and reports relative rotation. Torque into the rotor is torque out of the housing, so a motor bolted to a chassis shakes it. Structurally it is the same as the motor and electro-thermal resistor: one registered behavior owns ports of several kinds.

Full 3D is just another connector kind

When geometry genuinely is the physics — a linkage, a pendulum swinging free in space, anything whose inertia depends on configuration — a frame connector carries a pose as its across configuration and a wrench as its through load. Its derived spatial twist dotted with the wrench gives power. Bodies and joints constrain frames the way gears constrain shaft angles: a new connector kind and domain, not a new coupling mechanism.

Geometry derives artifacts, never hidden behavior

Declared shape may produce mass properties, render or analysis meshes, attachment coordinates and candidate contacts. Gear teeth are still drawn from the declared ratio rather than the ratio being silently inferred from teeth, and touching faces do not decide whether they are welded or lubricated. Every derived parameter and generated edge carries provenance; constitutive behavior remains explicit.

One graph, two views

Clicking a gear selects the same ObjectId as the canvas. The inspector can then show its attached behaviors, ports, φ, τ and flattened residuals. Both views query one model world rather than synchronizing separate documents.

What all of that costs is small and worth committing to now: a Visual binding type, a Frame connector kind, and the mount component. Design the frame kind now and implement only the 1D half, and the full 3D mechanical domain arrives later as a plugin instead of a rewrite — the same argument as the emulator backend, made about geometry.

All of that assumes a machine made of nameable parts. The case it doesn't cover — water, air, sand, anything with no parts to name — is next.

CAD is the reference, not the simulation

A CAD assembly is too important to be a decorative mesh and too incomplete to be the physics by itself. It gives us reference geometry, hierarchy, placement and durable places to attach meaning. The simulation model says what each occurrence is; runtime state says what it is doing now. Those are three representations of one identity rather than three documents kept in sync by names.

CAD asset                 Semantic model                  Runtime state
assembly + geometry  ←→   entities + ports + behavior  ←→   solver variables
        ↓                           ↓                           ↓
render / analysis meshes   selection + inspection        motion + deformation

Import preserves identity and hierarchy

Every CAD occurrence gets a stable simulation id independent of display names such as Part001. Assembly frames, units and source provenance survive import. Re-import matches occurrences by that provenance and reports ambiguity rather than silently attaching a motor model to the wrong shaft.

Physics lives in a companion model

The source CAD remains immutable. Selecting a shaft and giving it a rotational flange, marking two faces as electrical terminals, or assigning material and thermal properties writes simulation annotations beside the asset. The design can therefore be updated without baking physics into a vendor file or losing authored behavior.

One shape becomes several representations

The beautiful render tessellation, collision shape, thermal mesh and structural mesh are derived artifacts with different jobs. They share the same reference coordinates and provenance but are never mistaken for one another. A million-triangle display mesh is not automatically a useful contact or finite-element model.

Geometry may generate visible topology

Placement can calculate mass properties and propose contacts, mounts or thermal neighbours. Every result lands in the ordinary graph as a generated, inspectable edge; no importer is allowed to hide behavior in the scene. Units and coordinate frames are typed at this boundary because millimetres-versus-metres is a physics bug, not an import nuisance.

When the CAD object bends

The CAD shape is the undeformed reference configuration. The current configuration is state: a rigid placement plus a displacement field, x(X,t) = R(t)X + p(t) + u(X,t). The renderer still never owns physics; it evaluates that mapping after an accepted step and draws the resulting shape.

Deformation is an internal model behind ordinary ports

A flexible behavior may carry six rigid coordinates, twenty modal amplitudes, or fifty thousand finite-element displacements. Outside it exposes frame or distributed mechanical ports: compatible configuration across the boundary and conserved wrench or traction through it. Derived velocity–load products supply the mechanical power diagnostic.

Fidelity changes without rewiring

A bracket may be rigid for an enclosure study, modal for vibration, a beam or shell for a structural run, or a full FEM block for stress. Every representation honors the same mounts and boundary ports. Reduced and detailed versions are therefore interchangeable only when both declare the capabilities the scenario asks for.

Ports are attached to material coordinates

A bearing, terminal or thermal contact is anchored at a point or region in the reference body, not at a frozen world transform. When the body bends, the port and anything mounted there move through the same displacement map. Loads return through that port into the structural residual, closing the loop.

Analysis and display meshes share a map

The structural solver updates its own coarse nodes or modes; a precomputed interpolation maps those values onto render vertices, preferably on the GPU. The same map locates attached visuals and ports. Rendering can interpolate between committed steps for smoothness without inventing physical state.

Power is the invariant at every resolution

For a distributed mechanical boundary, transferred power is the surface integral of velocity dotted with traction. Discretized ports preserve the same rule: coarse-to-fine motion is interpolated, fine-to-coarse forces are accumulated, and total power must match. That one test constrains every modal reduction and mesh coupling we write.

Not every shape change means the same thing

Elastic deformation changes runtime state and springs back. Plasticity and damage change material history or the effective rest configuration. Editing the CAD changes reference geometry and invalidates derived meshes and surrogates. Fracture or new contact changes topology and becomes an explicit structural graph edit.

The first proof is deliberately smaller than a general solid-mechanics system: import a board or bracket, clamp named CAD faces, solve a coarse modal or plate representation, exaggerate the deformation visually, and verify that ports and attached parts remain on the moving material. That validates the representation seam before full FEM becomes a backend.

Fluids, and a million particles

Everything up to here quietly assumes the world is made of parts. A motor, a shaft, a gear: each one is a thing with a name, a handful of numbers describing what it's currently doing, and two ends you can attach something to. That assumption is the entire reason the connector graph works — you can only wire up boxes if there are boxes.

Water in a pipe is not like that. It has a different pressure and a different velocity at every point along the pipe, and there's no natural place to draw the boundary of a "part". Sand pouring through a hopper is worse: a million grains that only mean anything as a crowd. Neither one has two ends in any obvious sense, and neither can be summarized by three numbers without throwing something away.

So this needs a real answer rather than a hand-wave, and the answer is a ladder rather than a switch — three rungs, and the same components at every one of them. The useful thing to know first is that the question decides which rung you need, and most questions are answered from the bottom.

An analogy that does most of the work. If you want to know how long a delivery takes across a city, you model the road network: each road has a capacity and a travel time, and you never simulate a single car. If you want to know why one particular junction jams, you have to simulate the cars. Same city, two completely different models, and choosing the wrong one is either wasted months or a wrong answer. Fluid is exactly this, and the overwhelming majority of engineering questions are road-network questions.

Tier one — fluid as a plumbing diagram

The easy half, and the one that covers most of what anyone actually asks. A pipe becomes a behavior with a port at each end. For the first incompressible model, pressure is the across variable and signed volume flow is the through variable. Compressible or thermal-fluid connectors may add density, enthalpy and composition later without changing the across/through connection rule.

It really is the same as a circuit. A narrow pipe resists flow the way a resistor resists current. A tank stores fluid the way a capacitor stores charge. A long slug of moving water has inertia and doesn't want to stop, the way an inductor doesn't want to stop carrying current. This isn't a teaching analogy that falls apart when you push it — the equations are the same equations, which is exactly why the same solver handles both without knowing which is which.

"But a pressure wave travels along the pipe." Right, and that seems like it needs a field. It doesn't. Chop the pipe into a hundred short pipes in a row, each one still a dumb little component with two ports. A disturbance at one end now has to pass through all hundred to reach the other, so it arrives late, and it arrives changed. Wave behaviour falls out of a chain of simple parts. That's all water hammer needs, and it's how the Rijke tube gets a note out of a heated gauze.

What you get and what you don't. You get pressure and flow everywhere along the pipe, transients, resonances, pumps fighting each other, a valve slamming shut. What a handful of components can't give you is anything whose answer depends on the shape of the flow itself — the swirl behind the valve, how the sand piles up. If you didn't need that, you've lost nothing at all, and you got an answer in milliseconds instead of hours. Where a hot spot lands on a wall is the more interesting case, because it sits between the two rungs — next card.

This tier is not special. It's a domain plugin like electrical or thermal, built the same way and coupled the same way. None of the complications in the rest of this section apply to it — everything below is about the other half.

Tier one and a half — a wall made of five hundred parts

Straight answer to the question this raises: yes, you can find the hot spot, and usually without leaving tier one at all. Chop the wall into five hundred little thermal masses, wire each to its neighbours with a conduction component, and wire the ones facing the flow to the fluid nodes beside them. Five hundred ordinary components, the same ports, the same solver, no field code anywhere. The hot spot is then just the patch with the highest temperature.

It's the same trick as the pipe, in two dimensions. A hundred pipe segments in a row gave you a travelling pressure wave; five hundred thermal masses in a grid give you a temperature field. "Distributed" isn't a different kind of physics — it's the same primitive repeated with its neighbours wired up. And because they're ordinary components, everything else on this page still works on them: surrogates, validity envelopes, cross-domain assertions, live values on the canvas, expect wall.hotspot stays below 110 °C as a scenario line.

What that demands of the core. A behavior must declare parameter-sized port arrays, bulk connections and a residual count that may depend on discretization. Across compatibility and through conservation still apply patch by patch. Changing array length is an explicit structural edit that invalidates the affected coupling island.

One consequence to know about. Changing the mesh count is a structural edit rather than a parameter tweak — it changes how many equations exist, so it triggers a recompile and a re-initialization at the seam. That's already built for, but it means resolution is a dial that pauses rather than one you scrub while watching.

Where it runs out, and why there's no cliff. Five hundred nodes is comfortable. Fifty thousand is where our own solver stops being the right tool, and at that point the wall becomes a domain that solves itself internally and exposes a boundary — which is tier two. The important part is that it's the same wall with the same ports at every rung: one component, five hundred components, or one component with a specialist inside. Nothing above it has to be rewritten when it moves, which is the fidelity ladder from Detail on demand applied to a continuum.

The honest caveat. A hot spot is only as good as the heat arriving at it, and a 1D fluid network hands you a bulk temperature and a textbook heat-transfer coefficient, not a resolved boundary layer. That's genuinely adequate for a cold plate or a heatsink and genuinely not for a recirculation zone behind an obstacle, where the flow's own structure is what puts the hot spot where it is. When that's the question, both sides have to go to tier two — and the harness measures the gap between the two answers rather than us asserting one is fine.

Tier two — a real fluid solver, bolted on at its edges

When the question genuinely needs the swirl, you need the expensive thing: divide the space into a few million little boxes and track what's in each one, or track a few million particles and the forces between them. Millions of numbers, updated by code that has nothing whatsoever in common with our equation solver.

The decision that makes this tractable: we don't merge it. The tempting move is to flatten those millions of unknowns into our equation system so everything is solved together and uniformly. That's a trap. Our pipeline sorts equations, finds loops, and inverts small dense blocks — machinery that is excellent for two hundred equations and hopeless for two million. Meanwhile a CFD solver already has decades of specialized work behind it. Merging gets you the worst of both.

So it stays a box with pipes. On the diagram it is one behavior with an inlet and an outlet. Inside, it uses whatever solver and substeps it needs. At the boundary it speaks the connector's language: pressure and signed volume flow for the first incompressible domain. This is the same opaque-block mechanism used for contact and foreign subsystems.

Cheap version, same box. Once you've run the expensive thing, you can usually replace it with a fitted curve — a loss coefficient, a heat-transfer number — that reproduces what the ports did without any of the interior. That's the surrogate story from earlier applied to a continuum, and the harness that checks a surrogate against its detailed model doesn't care that the detailed model happens to be CFD.

How the handshake actually works, one step at a time

This is the part worth going slowly on, because it's where "two things that can't talk to each other" turns into "one simulation". The problem: to take a step, the rest of the model needs to know how the fluid box will respond — but it can't run a two-million-cell simulation once per guess, and a stiff solver guesses ten times a step.

So we ask a cheaper boundary question. At the beginning of one coupling step, the block publishes an affine relation f = Y·a + b. a contains all boundary pressures, f all boundary volume flows, b the response at the current history, and the full matrix Y says how perturbing any port changes every other port. Cross-port coupling is part of the contract, not a collection of independent slopes.

That matrix replaces the interior during speculation. The global Newton iterations operate on a small discrete-time boundary model rather than millions of cells. The relation may resemble a multiport conductance, but it is allowed to contain history and step-size dependence; calling it a resistor would throw away exactly the dynamics the boundary must preserve.

Then the step commits. Once everything agrees on a consistent answer, the fluid box is told: this is final, here is the pressure we settled on, advance yourself. Now it goes and does the expensive million-cell update, once, and only for a step that actually happened. Everything speculative was answered by the two numbers.

When the affine relation isn't good enough. A rollback-capable block may expose pure residual and Jacobian queries and participate in coupling iterations without committing state. A non-rewindable block cannot use that path: its coupling step is chosen in advance, its published relation is accepted as the approximation for that interval, and divergence is measured afterward rather than repaired by secretly replaying history.

Why this is one transactional seam. The block separates pure boundary evaluation from advancement into trial state and final commit. Native controllers, WASM, FEM and CFD differ in cost and rollback capability, not in the runtime's accepted-step protocol.

Boundary conditions aren't something we invented

Worth saying, because it makes the whole arrangement feel less like a trick. A fluid solver cannot run without being told what's happening at its edges — how hard the inlet is being pushed, or how much is flowing through it. Every CFD run in the world has that, and normally a human types it in once and it never changes. All we're doing is supplying those numbers from the rest of the model instead, freshly every step. And the acausal rule — pressures match where things join, flows into a junction cancel — is the bookkeeping that keeps the two sides consistent. Flutter is the case that proves it has to work in both directions at once: the wing's motion changes the airflow, and the airflow loads the wing, inside a single step.

A million particles is a storage question, not a physics one

A million particles are not a million Bevy entities. They are one opaque block-state owner registered under a BlockStateId, containing flat arrays and a spatial index. ECS tracks the semantic object, boundary behaviors and state handle; nothing outside reaches into particle storage. Distinct user-facing objects belong in ECS, homogeneous numerical fields belong behind a registered state boundary.

What we give up, said plainly

Three things, and none of them is a surprise once you see where they come from.

The coupling island loses the right to retry. A non-rewindable block forces a fixed, pre-agreed boundary step. It may substep internally, but the outer runtime does not accept the interval and then ask it to un-happen. Adaptive control stops at that boundary; a failure to advance is an explicit failed run rather than a hidden partial rollback.

Accuracy at the join is measured, not promised. Passing two numbers per step across the boundary is an approximation, and it introduces error that is genuinely hard to bound in advance. That's consistent with what's already been decided: we measure divergence per model and report it honestly, and we don't claim an end-to-end error bound we can't back up.

It's slow, and it should be. This tier is hours-not-milliseconds, so it's for the run where the question requires it, not for the parameter sweep. The parameter sweep uses the fitted surrogate, and the harness is what tells you whether that was allowed.

You can still watch it

The rule from the previous section holds without amendment. The fluid domain publishes a buffer for drawing — particle positions, a slice through the grid, a surface — and the renderer reads it exactly the way it reads a gear's angle. One-way, with the solver's own state as the only truth. Watching a million particles is the same kind of operation as watching one gear turn, which is a good sign the boundary was drawn in the right place.

Where this lands in the plan: tier one is an ordinary registered domain. Tier two is deliberately later. What we owe it now is parameter-sized port arrays and the transactional multiport block contract — pure boundary evaluation, trial advancement, commit and declared rollback capability — shared by CFD, FEM and foreign firmware.

A resistor is three things at once

Everything so far has been careful about coupling between components and quiet about coupling inside one, which leaves a hole. Real parts aren't single-domain. A resistor on a board is an electrical element, a heat source with a thermal mass of its own, and 0.4 grams sitting at a particular place. A motor is a winding, a rotor, a lump of iron that gets hot, and something bolted to a chassis that shakes it.

The answer is composition with explicit identity: one semantic object carrying several behaviors. An ObjectId names the real part or CAD occurrence; each equation-producing BehaviorId, boundary PortId and numerical StateId remains separately addressable. An ECS may store those behaviors on the object or on related entities without confusing implementation layout with physical identity.

One object, several behaviors

The resistor object owns electrical behavior, thermal storage, mass and placement. A dedicated electro-thermal bridge behavior owns the equations P = I²R and R(T); neither neighbouring domain reads the other's state. Nothing in the core knows the word “resistor” — it sees registered behaviors, typed ports and stable state handles attached to one object.

Inside a part is equations; between parts is ports

Constitutive facts about what a part is belong to its behaviors; relationships to other objects belong to ports and graph edges. The electro-thermal bridge converts electrical dissipation into signed heat flow and lets temperature affect resistance. Its thermal connection to the copper underneath is an ordinary selectable edge. Current hogging appears only when both internal bridge equations and external topology close the loop.

The same parts, wired three different ways

This is the part that surprised me into writing the section. Electrically, a resistor's neighbours are whatever the netlist says. Thermally, its neighbours are whatever it physically touches — the pad beneath it, the air above it, the part sitting next to it. Mechanically, its neighbour is whatever it's mounted to. Those three neighbour sets have almost nothing in common, so what we have is three quite different connection topologies over one shared set of entities. That's the real answer to "how do we model heat distribution": not a special mode of the electrical model, but a second graph over the same parts.

Where the thermal graph comes from. Not from typing it in — a board with four hundred parts has a thermal topology nobody is going to wire by hand. It's derived from placement: the board is the discretized wall from the previous section, a grid of thermal masses each exposing a port, and every part's thermal port is connected to the patch it sits on. Overlapping pads conduct, adjacent patches conduct, exposed patches convect to ambient. Heat distribution is then just the temperature field across that port array, and the hot spot is the patch with the highest number.

Which is a nuance against "geometry parameterizes; it doesn't derive". Deriving physics from a mesh, still no. Deriving topology from placement — which patch touches which — yes, and the difference matters: the result lands in the graph as ordinary connections you can see, select and delete, rather than as behaviour hidden inside a solver. Generated edges are marked as generated, so re-running placement replaces them without clobbering a wire someone added by hand.

And the graphs move independently. Slide a part two centimetres across the board and its thermal neighbours change completely while its electrical neighbours don't change at all. Same entity, same netlist, different heat path. That independence is the whole reason these are separate graphs rather than one graph with tags.

Weight is a property, not a domain

Worth not over-building. Mass is something several domains read, and it shows up at three levels of seriousness. Total mass and centre of mass of an assembly are a query over the graph — a sum over everything carrying a mass component — and not a simulation at all, which makes them nearly free and worth having early. Static load, where the board sags and a connector takes weight, is the mechanical domain with parts as loads. Only the third level costs anything: feeding an inertia tensor to a 6-DOF domain, where where-each-part-sits starts to matter dynamically. No weight domain, no weight solver.

Gravity, ambient, vibration: sources, not globals

Environmental influence remains explicit, but not every source uses an acausal power connector. Ambient temperature is a thermal boundary; a shaker is a mechanical boundary; gravity is a directed field signal consumed by mass behaviors, with gravitational potential energy accounted by the mechanical island. Authoring sugar may broadcast a field to many objects, but it generates visible provenance-bearing subscriptions rather than a hidden global read.

Vibration lands differently on different representations

And here's the case that has no clean answer yet. Take the easy half first. Bolting a thing to a shaker table and shaking it is not a new mechanism: it's a mount whose motion is dictated from outside rather than worked out by the solver — like a hand holding one end of a rope, deciding that end's motion and leaving the rope to sort out the rest. Small piece of ordinary work.

The hard half comes from a decision made earlier on this page: we deliberately keep several models of the same real object, and pick one per run. Shaking is where that catches up with us. The same shake is three completely different questions depending on which model happens to be loaded, and for one of the three the honest output isn't a number at all — it's a refusal.

First, what "representation" means here. A motor in this system isn't one model. It might be a detailed one with a shaft that can twist and a case that can flex; it might be a cheap stand-in fitted to reproduce the same input-output behaviour — a box that takes electrical power in, produces torque out, and warms up according to a curve. You load the detailed one when the question needs it and the cheap one when you're sweeping a thousand parameter combinations. The trap is that these are not the same model with a detail knob turned down. They are built out of different pieces. The detailed one contains somewhere that can physically move; the cheap one may contain nothing but arithmetic. That difference stays invisible right up until you ask a question that needs the missing piece — and shaking is precisely that question.

Response one: it resonates. If the model has somewhere to flex — a circuit board treated as a springy plate rather than a rigid slab — then shaking it behaves like pushing a swing. Push at roughly the rate the swing already wants to swing at and small pushes accumulate into large motion; push at the wrong rate and they cancel out. Every physical object has a handful of rates like that, each with its own shape of wobble, and the standard word for one of them is a mode. Shake near a mode and the motion grows until damping catches it. This is what most people picture when they hear "vibration test", and it needs nothing new from us: it's the mechanical domain doing its job, provided the model was given the freedom to move in the first place.

Response two: it leaks into other domains. Shaking a board flexes the solder joints holding parts onto it. Flex a joint enough times and it starts to crack; a cracked joint carries current worse; carrying current worse means more heat where the current is forced through what's left; and heat makes the crack grow faster. Mechanical to electrical to thermal and back round again. Neither the mechanical domain nor the electrical domain knows any of that, and neither should — the loop only exists if some component owns it: a solder-joint model with a mechanical port that counts how hard and how often it's been worked, and an electrical resistance that rises as the count does. That's the rule from two cards up in its natural habitat — coupling inside a part is equations, coupling between parts is ports — and this is the example that made the rule worth stating.

Response three: nothing at all, silently. If what's loaded is the cheap stand-in — a box with a temperature and an efficiency curve — there is nothing inside it that can move. So the shaking isn't absorbed, isn't damped, isn't reported as small. It does not exist. The run completes, the plots look clean, and they describe a machine that as far as its own model is concerned was never shaken. That's the dangerous one, because nothing about it looks like a failure.

Why that's a different failure from leaving an envelope. An envelope exit is a stretched answer: a fit that was measured between 20 and 80 °C is being run at 95, so it's probably drifting — warn, record, carry on, which is already decided. What's happening here isn't a stretched answer, it's a category error, like asking a bathroom scale how tall you are. It won't give you an inaccurate height; there is no height in there to give. So this shouldn't surface as a warning buried in a finished run — it should be refused at the moment you wire it. Concretely: every representation declares which kinds of port it carries — mechanical, electrical, thermal, hydraulic. A shaker's plug is mechanical. If the model you're plugging it into has no mechanical socket, the connection is rejected there and then, with a sentence saying what's missing and which other fidelity of this same part does have it. Failing at wiring time costs you thirty seconds; failing silently costs you the month you spent believing the plot.

And an excitation has to be spreadable. One more thing that has to be built rather than assumed. In the previous section a wall got chopped into five hundred patches so hot spots could show up somewhere on it. Shake that wall and you owe the solver a motion for each of five hundred patches. Shake the one-box version of the same wall and you owe it a single motion. Same physical shake, wildly different amounts of input — so a shaker can't simply hand over "the motion" and be done. It has to know how to spread one description of shaking across many pieces, and results have to travel back the other way, five hundred separate motions collapsed into the one number the coarse model deals in. Spread out, collapse back. Those two directions are one object, and we already need half of it: turning a detailed model into its cheap stand-in is the collapsing direction. Build the map once, on purpose, usable both ways — the alternative is two half-finished versions growing in separate corners of the codebase without anyone noticing they were the same thing.

The uniform case is easy, and that's the trap. If the whole wall is bolted flat to the table and moves as one rigid slab, spreading is just copying: every patch gets the same motion, and you could write that in an afternoon and believe you'd solved it. But the shakes worth simulating aren't uniform. One edge is clamped and the other is free, so the far edge swings further. The table twists as well as heaves. A wave takes real time to cross the panel, so the far side is still going up while the near side has started coming down. In every one of those, spreading means having a shape — a stated rule for how the single number you were handed is distributed across the five hundred you owe. That rule is a physical assumption, it's usually wrong at the edges, and it should therefore be a named, visible, swappable thing rather than a loop buried in the shaker's update function.

The two directions use different arithmetic. Across fields — angle, temperature, pressure — are copied or interpolated from coarse to fine. Conserved through quantities — torque, heat flow, volume flow — accumulate from fine to coarse. Any averaged observation needs an explicit physical weight such as area, mass or heat capacity; a fingernail-sized patch must not vote as loudly as the rest of a wall merely because both are one array entry.

Each connector kind supplies the honesty check. Mechanical maps preserve twist–wrench power, electrical maps preserve voltage–current power, hydraulic maps preserve pressure–volume-flow power, and thermal maps preserve signed heat-flow balance while tracking entropy production separately. Choose a spreading operator and conservation constrains the corresponding collapse operator. The map is an ordinary visible behavior between a scalar port and a port array, reusable for vibration, ambient temperature and distributed pressure without claiming their energetics are identical.

What this commits us to is small and explicit: a bridge behavior may own ports of several kinds and their constitutive equations; generated connections land as ordinary editable edges with provenance; and every representation declares its connector capabilities so an unanswerable scenario fails during wiring rather than after a run.

Drive it like the real thing

The honest test isn't applying a torque to a shaft — it's wiring a real supply to a real bridge to a real motor under a real load, running a controller that doesn't know it's in a simulation, and then asking what the whole system did. The interesting assertions cross domains: volts in one, shaft speed in another, junction temperature in a third, all in a single statement about one run.

scenario "cold start under load" {
  supply.v      = 24
  load.torque   = ramp(0 → 0.4 N·m over 2 s)
  controller    = wasm("firmware/foc.wasm") @ 10 kHz

  expect motor.speed          reaches 3000 rpm within 250 ms
  expect motor.speed          settles within 2% of setpoint
  expect bridge.junction_temp stays below 85 °C
  expect supply.current       never exceeds 12 A for longer than 50 ms
}

Assertions are temporal, and about the system

Reaches-within, settles-to, stays-below, never-exceeds-for-longer-than. These are statements about a trajectory rather than a final value, and they name signals from any domain in the model. A failure reports the moment it happened and the surrounding trace, not a boolean.

Causal blocks in an acausal graph

Worth being precise about, because it sounds like a contradiction and mostly isn't. A controller is causal — it reads sensors and writes commands — while the network around it has no preferred direction. Both live in the same graph, and they're reconciled in one place: the structural analysis that already runs on every recompile.

What that analysis does anyway. Flattening the graph produces a pile of equations and a pile of unknowns, with nothing yet saying which is supposed to produce which. Matching is the step that decides: this equation is the one we'll use to compute that unknown. For an acausal component that's the entire point — it contributes equations with no assigned direction and lets matching choose. Once everything is matched you can sort it, and most of a real model sorts into a plain sequence: solve this, substitute the answer, solve the next.

Tearing is what you do when it won't sort. Some groups of equations are circular — this one needs that one's answer and that one needs this one's — so no order works and they have to be solved together. That's an algebraic loop, and solving forty simultaneous equations numerically is expensive: a Jacobian and a matrix factorization on every iteration. Tearing shrinks the problem. You pick one or two variables inside the loop, guess them, and with those values in hand the rest of the loop stops being circular and sorts into a chain you can simply evaluate. Follow the chain all the way round and you arrive back at an equation you deliberately set aside; if the guess was right it balances, and if it doesn't, you adjust the guess and go round again. A forty-unknown numerical solve becomes iteration on one or two.

Concretely. In a loop of resistors you can't get a voltage without knowing a current and can't get a current without knowing a voltage. So guess the current in one branch, compute every other voltage and current from it in order, and check whether the branch you started from still agrees with itself. A handful of rounds and it's done. The payoff is that the expensive linear algebra is sized by the number of torn variables rather than by the size of the loop, and good tearing is most of why Modelica tools stay interactive on ten-thousand-equation models.

A causal block just arrives pre-matched. It says: these ports are inputs, these are outputs, the map between them is opaque. Matching honors that rather than deciding it. Nothing about the algorithm changes — a causal block is a constraint on the matching, and a constrained matching is the same algorithm with some of its choices already made.

The one genuinely hard case is direct feedthrough inside a loop: a causal block whose output depends algebraically on its input at the same instant, sitting in a cycle. The guess-and-check round trip above would have to pass straight through it, and it can't, because the block is opaque — there's no equation to rearrange. So either the block declares how its output moves with its input — its input-output Jacobian — or we refuse to place it in an algebraic loop and say plainly why.

And a Jacobian, since the word keeps turning up. It's a table of slopes, and nothing more than that. For every input and every output there's one number answering "if I nudge this input a little, how far does that output move?" With one input and one output it collapses to a single number — the slope of a line. Solvers want it because knowing which way and how fast everything moves lets them aim straight at an answer instead of guessing at one, and it's the same object as the second of the two numbers a fluid box publishes at its ports.

Sampling makes the common case easy. A controller running at 10 kHz holds its output constant across the step. A held output is a known value, not an unknown — so the controller drops out of the algebraic system entirely and contributes nothing to solve. The realistic case, a sampled digital controller, is also the cheapest one.

Three tiers of foreign code

You're right that WASM alone is too narrow. It assumes a recompile you may not be able to do — sometimes all you have is a .bin someone handed you. So the adapter should be a tier, not a technology.

Native. A Rust block compiled into the binary. No boundary, no marshalling, full speed. For controllers we write ourselves, and for the reference implementations everything else gets compared against.

WASM. Anything with a WebAssembly target — Rust, C, C++, TinyGo, increasingly Python. Sandboxed, deterministic, and a snapshot is a copy of one linear memory. The right tier when you have source but not our language.

Emulated target. When you only have the binary, run the binary. An instruction-set emulator for the actual part — Cortex-M being the obvious first family — executing the unmodified firmware image, with our peripheral models wired to its memory-mapped registers. The firmware reads an ADC register we populate from the simulated analog front end and writes PWM registers that drive the bridge, and it cannot tell the difference.

What emulation costs. Somewhere between ten and a hundred times slower than a native block, and it ties us to specific chip families, so it isn't the default. But it's the only tier that's honest about interrupt latency, register write timing, and what the compiler actually emitted — and the only one that works at all on a binary blob.

The interface is the real design. All three tiers implement one block trait, so which tier a subsystem uses is a property of how it was loaded and not something the graph or the solver knows about. Get that trait right and adding the emulator later is a backend, not a redesign. Settled below: native and WASM get built, emulation is the third backend behind the same trait, built the first time a binary-only firmware makes it necessary.

Which chip, then. The joke lands closer than it should, because two chips are involved and both matter. This machine is the target of the native tier — compile the same firmware source for the desktop, run it in-process at full speed, and treat it as the reference the other tiers are diffed against. That's the tier most debugging will actually happen in, and it costs us nothing but a cargo target. The emulated tier targets ARM Cortex-M, which is a different animal from anything in a laptop: M-profile, Thumb-2 only, no MMU, peripherals bolted straight onto the address map. Even on an ARM desktop you can't just execute it — different profile, different encoding, nothing to reuse but the vendor's name. Which is fine; that's what an interpreter is for, and Cortex-M is the family with the best existing cores to lean on.

What picking the family decides today. Almost nothing about the emulator and everything about the peripherals, which are the part we build first: an ADC with real quantization and conversion delay, an advanced-control timer that inserts dead time, a tick source and an interrupt controller with honest latency. Those are ordinary components in the graph, and they're reusable across all three tiers — the native-tier firmware talks to the same modeled ADC the emulated image does, just through a shim instead of a memory-mapped register.

The tiers have to be interchangeable to be worth having. The real payoff is running the same firmware at two tiers and diffing: native or WASM for the fast parameter sweep, emulated for the run that has to be exactly right about interrupt latency. That only works if a tier swap doesn't change the block's interface to the graph — which is the surrogate-harness argument again, applied to code instead of physics.

The re-entrancy problem

The part that needs the most care, and the reason the block interface has the shape it does. A foreign block gets called many more times than there are timesteps, and most of those calls must not be allowed to change anything.

Why pure evaluation is called repeatedly. An implicit step runs Newton iterations at trial states. Later, rollback-capable islands may also reject a step or bisect an interval to locate an event. The fixed-step first slice does neither globally, but the transaction contract is designed now so adding them does not change component semantics.

The structural fix. Split evaluation from advancement. eval(t, inputs) → outputs is pure and may be called any number of times; advance(h) may mutate and is called exactly once per accepted step. FMI makes the same split for the same reason, and it should be the first trait we write.

Real firmware won't cooperate. Actual control code mutates on every call — that's what an integral term is. So for anything we didn't write, we snapshot instead: capture before the step, restore before each retry, commit on acceptance. The cost is reassuringly uniform across tiers — a Clone for native, one linear-memory memcpy for WASM, registers plus RAM for the emulator. Tens of kilobytes a few thousand times a second is nothing.

Side effects need deferring too. A block that logs, traces, or bumps a counter during a rejected step has corrupted its output even though its state was restored. So block-visible I/O is buffered and flushed only when the step commits — which is also part of what makes a run reproducible.

The machinery pays for itself elsewhere. Once whole-model snapshot exists, canvas undo, rewind-and-replay debugging, and the checkpoint before a structural edit are all the same operation. Worth building properly the first time.

Rate, budget, and sandbox

A block runs at its own rate with explicit sample-and-hold, so a 10 kHz control loop sitting on a plant stepping at microseconds is an ordinary scheduling fact rather than a special case. Fuel limits keep a hung or hostile block from taking the simulation with it, and the sandbox means running someone else's firmware isn't a decision you have to think hard about.

The compiler produces a disposable numerical program

struct CompiledModel {

Compilation validates connector compatibility, collapses connected ports into nodes, allocates dense views over stable state ids, emits behavior and connection residuals, matches equations to unknowns, partitions strongly connected coupling islands and precomputes Jacobian sparsity. The first machine is one island; tearing and incremental compilation optimize the same representation later.

The motor is the bridge behavior

Its electrical residual is V = Ri + L·di/dt + Kₑω; its rotational contribution is τ = Kₜi. The load contributes J·dω/dt = τ − τ_load and dθ/dt = ω. The ideal gear contributes θ₁ = nθ₂ and τ₂ = −nτ₁. No behavior calls a neighbour: registered residuals and connection equations close the island.

One accepted-step protocol owns mutation

loop {
    let mut step = state.begin_trial();
    scheduler.apply_due_events(t, &mut step); // controller state is trial state
    runtime.solve_islands(&compiled, t, dt, &mut step)?;
    runtime.commit_step(dt, step, &mut state)?; // opaque blocks advance once here
    publish_observables(&state.committed());
    t += dt;
}

Newton repeatedly evaluates R(xₙ₊₁, xₙ, u, Δt), solves JΔx = −R, and updates dense trial views until converged. Before the commit barrier, failure discards controller integrals, solver values and rollback-capable block state together. A non-rewindable block advances once at the barrier and makes any later failure terminal. Implicit midpoint is the first island integrator because it treats the electro-mechanical loop coherently.

The controller is sampled, causal and cheap

At 10 kHz it reads committed speed, advances its PI integral in the step transaction and publishes a clamped duty cycle. The fixed coupling step lands exactly on controller events; output is held between them and is known during Newton iteration. A discarded transaction may deterministically replay the event without double-advancing state. Native Rust comes first; WASM and emulation later implement the same contract.

The 3D scene reads the same values the tests do

#[derive(Component)]
struct VisualBinding {
    angle: StateId,
    axis: Vec3,
    offset: Quat,
}

fn project_state(binding: &VisualBinding, state: &CommittedState) -> Quat {
    binding.offset
        * Quat::from_axis_angle(binding.axis, state.angle(binding.angle).radians() as f32)
}

The motor rotor and each gear read solved angles by stable handles. Render interpolation may smooth between committed states but never advances them. A brownout, load change or controller fault therefore appears as the corresponding visible slowdown without any animation-specific dynamics.

Done means the whole path is falsifiable

A deterministic scenario supplies 24 V, commands 3,000 rpm, drives a 4:1 gearbox and applies an inertial load. Tests bound current, settling time and coast-down; check the gear constraint, electrical transfer and rotational power balance; and confirm that visual bindings read the exact state ids used by assertions. The machine on screen and the test report must be two views of one run.

Emergence as the acceptance test

The proof that a multi-domain core is rigorous isn't that a pendulum swings. It's that you change one value at one edge of the system and behavior nobody encoded falls out the other end — because the coupling was honest enough to produce it. So the acceptance suite should be a list of documented surprises, each with published numbers to fail against.

Every one of these has the same shape: a single parameter at a boundary, a qualitative change in what the whole system does, and a reference measurement from the literature.

mechanical

Kapitza's inverted pendulum

Shake the pivot up and down fast enough and the upright position becomes stable. Nudge the bob and it returns to vertical, standing on nothing.

Proves: integrator fidelity and timescale separation. The effect lives entirely in the averaged residual of a fast oscillation, so a step size that's merely adequate erases it completely.

mechanicalstructural

Huygens' coupled clocks

Two pendulum clocks on a shared flexible beam settle into exact anti-phase within the hour, whatever their starting positions. The beam moves by micrometers.

Proves: weak coupling survives our connector layer. All the information passes through a tiny amount of momentum exchange — round it away and the synchronization never appears.

electricalthermal

Current hogging

Two identical devices in parallel should split the load evenly. With a positive temperature coefficient they self-balance; flip that coefficient negative and the marginally hotter one draws more current, heats further, and takes all of it. Same topology, same parts — the sign of one derivative decides whether the board survives.

Proves: the electro-thermal loop closes in both directions — dissipation heats the part, temperature moves resistance — with no special case anywhere.

thermalacoustic

The Rijke tube

A heated gauze a quarter of the way up an open tube makes it sing. Steady heat in, a loud pure tone out, with no oscillator anywhere in the model. Slide the gauze past the midpoint and it falls silent.

Proves: Rayleigh's criterion emerges rather than being asserted — heat added in phase with the pressure wave feeds the mode. The position dependence makes it sharply falsifiable.

hydraulicstructural

Water hammer

Close a valve in a tenth of a second and pressure spikes to many times what the pump can deliver — routinely enough to split the pipe.

Proves: we're carrying compressibility and a finite wave speed. An incompressible network solve cannot produce this transient at all, and the Joukowsky prediction gives us an exact number to hit.

fluidstructural

Flutter

Below a critical airspeed the structure damps any disturbance. A few metres per second above it, the same structure starts extracting energy from the airflow and shakes itself apart. Nothing changed but one boundary value.

Proves: the system finds a stability boundary we never wrote down — the phase lag that inverts the sign of the damping is a consequence of the coupling, not a term in it.

Two things follow for the design. Integrators have to be good enough that these effects survive discretization, which argues for energy drift being a first-class diagnostic rather than something you discover later. And every scenario needs a stored reference trace, so a regression shows up as a number rather than as a simulation that looks a bit wrong.

Decided

Settled in review, and treated as fixed unless something forces a revisit.

Controller-to-gears first

The first vertical slice is a sampled controller, voltage source, DC motor, 1D rotational drivetrain and visible 3D gears. It proves causal and acausal composition before the general 6-DOF domain.

Typed quantities everywhere

Authoring APIs, behavior parameters and connector schemas use typed quantities. The compiled numeric core stores canonical-SI scalars beside validated quantity metadata, so sparse algebra stays efficient without allowing metres and radians to connect accidentally.

An interactive sandbox

The product is a canvas where you can watch the whole system at once. The core still runs headless, so batch sweeps and regressions never need a window.

CAD is a first-class reference

Imported assembly identity, hierarchy, units and frames are preserved. Simulation behavior lives in a companion model; re-import updates geometry without pretending CAD alone contains the physics.

Deformation is physical state

CAD supplies the reference configuration. Rigid placement, modal amplitudes and finite-element displacements belong to the solver; render meshes and attached ports are projections of committed state.

Analysis and render geometry are separate

Collision, thermal, structural and display meshes may differ, but share provenance and explicit interpolation maps. A detailed visual mesh never silently becomes a numerical model.

Connector kinds own their energetics

Across equality and through conservation are universal; energy accounting is not. Each connector kind defines signed transfer and diagnostics, and every coarse-to-fine map preserves that declared balance.

Objects and behaviors have separate identities

CAD occurrences and conceptual parts use ObjectId; equation providers, ports and state use BehaviorId, PortId and StateId. One part may therefore compose many domains without duplicating physical identity.

A minimal registry exists from day one

The compiler consumes registered descriptors rather than a closed component enum. Built-ins stay simple, but independent domain plugins do not require later surgery on the compiler.

The StateStore is authoritative

Stable numeric and opaque-block state ids live outside compiled layouts. ECS behaviors, solvers, renderers and assertions refer to the same registry; private block memory participates through declared transaction capabilities.

Same-machine repeatability

Reproducible run to run on one machine. Cross-machine bit-determinism isn't a goal, though we won't gratuitously design it out.

Our own solvers, behind traits

Simple residual, integration and constraint solvers sit behind focused interfaces. A specialist engine such as Rapier would enter as an opaque rigid-body/contact domain behind mechanical ports, not masquerade as a drop-in replacement for the global DAE runtime.

Hybrid domains

Not everything is an equation. The connector graph is the contract; how a domain solves inside is its own business. The mechanism is Black boxes at the boundary above.

Native project format

Serialize objects, behaviors, ports, initial state, asset manifests, annotations, provenance, scenarios, solver configuration and edit history. Derived meshes and compiled layouts remain rebuildable caches. Modelica import waits until our semantics settle.

Warn on envelope exit

Warn and record by default, auto-escalation opt-in per model. No silent fidelity switches.

Per-model error, honestly

Measure divergence against the detailed run and surface it; claim nothing about composed end-to-end bounds we can't back up.

Declarative assertions

A form the runner can introspect, so a failure can plot the signal it was about. Script escape hatch for the rare thing the form can't say.

Peripherals are modeled, not approximated

You weren't misunderstanding — the ADC, sampling clock and PWM timer are real components with quantization, conversion delay and dead time of their own. Emulating the processor is the separate matter, settled in the next card.

Native and WASM first, emulation as a backend

Between them the first two tiers cover everything we write ourselves. Emulation lands behind the same block trait the day a binary-only firmware forces it — a week, not a quarter. Target family is ARM Cortex-M, which is really a decision about which peripherals get built first.

The integrator belongs to a coupling island

Strongly connected flattened equations advance coherently under one island policy; opaque blocks may substep internally. The first electro-mechanical island uses fixed-step implicit midpoint, with measured convergence and connector diagnostics.

Rewiring preserves surviving state

Stable StateIds survive recompilation while disposable dense layouts change. Only dirty coupling islands rebuild and re-initialize; undo restores a transactional snapshot rather than attempting to invert a seam solve.

Rhai for authoring

Native Rust types cross the boundary with no marshalling layer to maintain, and authoring scripts are not where we need speed. Separate question from foreign subsystems — conflating the two is most of what made it feel hard.

Open questions

Two left. The first mechanical slice, 3D projection, CAD's role and deformation semantics are settled; what remains is one question about the practical CAD ingestion path, and one about where reduced models come from.

01

What is the first authoritative CAD ingestion path? We need engineering assemblies with stable occurrence identity, units and frames, but the renderer ultimately wants tessellated assets and the simulation wants separately derived analysis representations. Treating a display format as the source loses engineering semantics; embedding a full CAD kernel immediately risks making import the whole project.

My lean: define a kernel-neutral internal assembly manifest first, support glTF as the immediate visual carrier, and add STEP ingestion through a narrow adapter that emits the same manifest plus tessellation. Store simulation annotations against our stable occurrence ids and source provenance rather than against either format's transient node names.

The internal manifest is the seam. It records assembly occurrences, parent-child transforms, units, source keys, material hints and references to derived assets. Importers end there; the graph authoring tools begin there. That keeps a future proprietary importer or cloud conversion service from leaking into the solver.

Re-import is the real acceptance test. Import a gearbox, annotate its rotor and mounts, change one bracket in the source assembly, then import again. Unchanged occurrences must retain their simulation identities and annotations; changed or ambiguous matches must be surfaced for review.

What stays deliberately manual. Geometry may propose contacts, joints and thermal neighbours, but a person accepts the simulation meaning. The importer can know two faces touch; it cannot know whether they are welded, lubricated, insulated or merely coincident.

02

Who produces the reduced models? Automatic order reduction is a deep specialty and only behaves for linear time-invariant subsystems; hand-authored surrogates work everywhere but rely on someone knowing the physics.

My lean: hand-authored surrogates plus a validation harness that runs both fidelities and reports divergence. Automatic reduction lands later, for the linear cases where it's actually sound.

What a surrogate actually is. For the board: a lumped RC network on the thermal port — junction-to-case resistance, case-to-ambient, one thermal mass — plus an efficiency curve on the power port. Five or six numbers standing in for a few hundred nodes. The skill is entirely in choosing that structure; nothing about it is laborious once chosen.

Where the numbers come from. The human picks the structure, an optimizer picks the constants — least squares against traces from the detailed run. That split is what makes "hand-authored" affordable: you supply physical judgment about which effects survive the reduction, not curve-fitting done by hand.

What the harness measures. Both fidelities run the same scenario under identical boundary conditions with every port recorded, and divergence comes back as numbers — peak error, RMS, and the moment it went worst — so a regression is a value that changed rather than a picture that looks a bit different. This is also the first real consumer of the determinism guarantee, since the comparison is only meaningful if both runs are reproducible.

And it plots, obviously. The numbers are what a regression test compares; the plots are what a human uses to work out why. Both, from the same recorded traces: each port overlaid detailed-versus-reduced, the difference drawn underneath on its own axis with the worst moment marked, and the sweep rendered as a map of divergence against amplitude and frequency with the validity envelope shaded on top — so the envelope is something you can look at rather than a threshold in a config file. Comparison against a stored reference trace gets the same treatment, which means the phenomena suite and the surrogate harness share one plot view. It belongs in the app next to the inspector, and headless runs write the same data out for a report.

Excitation is most of the difficulty. A surrogate matched at steady state can be wildly wrong on a transient, so the harness sweeps rather than spot-checks: step response, a frequency chirp, and the duty cycle you actually care about. Nearly every surrogate failure in practice is a model that was only ever checked at DC. The most realistic excitation available is the real one — drive the subsystem with its actual controller, as above, and compare fidelities under the load it will actually see.

The envelope falls out of the sweep. This is the part I like most — the region where divergence stays under threshold is the validity envelope we settled on above. It stops being a promise someone wrote in a comment and becomes a measured artifact of the fit, re-derived every time either model changes.

What it costs to build. A scenario runner, a port-trace recorder, and a comparison report. Those same three pieces are what the phenomena above need in order to run as regressions, so this is shared infrastructure rather than a detour — which is most of why I'd start here rather than with the automatic path.

What unlocks automatic reduction later. Balanced truncation needs a linear state-space, so behavior descriptors must be able to emit or derive Jacobians around an operating point. Register that hook now, even unused, and automatic reduction becomes available for suitable linear islands without a redesign.

Build order

  • Core skeleton. Model world, typed quantities, separate object/behavior/port/state ids, transactional StateStore, edit commands and the minimal descriptor registry. Built-ins are simple; compiler extensibility is real.
  • Connector compiler. Electrical across/through ports, graph flattening, residual assembly, stable-to-dense state mapping, coupling-island partitioning and a linear/Newton solve, proven on an inspectable voltage divider.
  • Controller-to-gears slice. Sampled PI control, voltage source, electrical–rotational motor bridge, ideal gears, inertia and one fixed-step implicit-midpoint island. Done when tests and visible gears read the same committed StateIds.
  • CAD semantics. The internal assembly manifest, stable occurrence mapping, glTF visual import, companion simulation annotations and a re-import test that preserves meaning across a design edit.
  • Flexible projection. A coarse plate or modal body attached to CAD reference geometry, with material-anchored ports and a render-mesh interpolation map. Done when a clamped part bends and everything attached follows it.
  • Second coupled phenomenon. Electrical and thermal behaviors close the loop through an electro-thermal resistor bridge, with current hogging or self-balancing as the acceptance result.
  • Hierarchy and fidelity. Subsystems as behaviors, one hand-authored surrogate beside its detailed model, and the harness that measures port divergence and connector-specific transfer error between them.
  • Live canvas and scripting. Build, rewire and inspect a running model; add incremental recompile, Rhai over the same graph API, scenario files, traces and comparison plots.
  • Foreign subsystems. Native and WASM blocks behind the transactional block contract, with declared rollback capability, snapshot/restore and modeled peripherals. Add emulation when binary-only firmware demands it.

Implementation plan

Build order says what gets proven in what sequence. The controller-to-gears slice above is the concrete first implementation; this is the long-lived layering it grows into. The point is to fix only the seams that would be expensive to move later.

sim-core              ModelWorld, registry, ids, quantities and StateStore
sim-compile           pure snapshot compiler, matching, islands and sparsity
sim-solve             integrators, Newton/linear solve and transactions
sim-dynamics          integration, discrete events and numerical analysis
sim-geometry          CAD manifests, reference frames and projection maps
sim-domain-*          independently registered physical behavior crates
sim-blocks            native, WASM and opaque-solver adapters
sim-app               Bevy canvas, 3D projection, inspectors and plots
sim-phenomena         scenarios, traces, comparisons and phenomena

The dependency arrows only point downward, and sim-core depends on bevy_ecs rather than on bevy. CAD semantics and projection maps live in headless sim-geometry; the renderer consumes them from sim-app. Domain crates depend on core contracts, never on the app or on one another; bridge behaviors explicitly import only the connector kinds they join.

Six contracts, and everything else is negotiable

ConnectorDescriptor defines across/through schemas, connection equations and energy diagnostics. BehaviorDescriptor defines parameters, stable state, ports, residuals and Jacobians. DomainPlugin registers descriptors without controlling stepping. Block declares evaluation, trial advancement, commit and rollback capability. Integrator advances a compatible coupling island. GeometryProjection maps reference-space CAD points, ports and render vertices from committed rigid or deformation state.

The compile pipeline is a pure function

Immutable model snapshot in, compiled islands out. Flatten, match, partition, tear, index-reduce, emit residuals, stable-to-dense mappings and sparsity. It writes no model or runtime state, which makes it directly testable and makes incremental compilation a memoized form of the same function rather than a second path.

State is the only mutable truth

The transactional StateStore registers stable numeric and opaque-block state identities. ECS behaviors hold handles; solver arrays are dense trial views; transforms, render-deformation buffers and display meshes are projections; CAD is immutable reference data. Rewiring, undo, replay, flexible visualization and fidelity changes all follow from that arrangement.

The test spine exists before it's interesting

Scenario runner, port-trace recorder and comparison report land alongside the first domain, while there's still almost nothing worth recording. Retrofitting determinism and reference traces onto a system that grew without them is the standard way this kind of project quietly stops being trustworthy, and the same three pieces are what the surrogate harness and the phenomena suite both run on.

What we're deliberately not building yet

Automatic model-order reduction, Modelica import, processor emulation, general contact, fracture, cross-machine determinism, full FEM and general 6-DOF mechanics. The reference-geometry, frame-port, block and projection seams are specified now so these arrive as domains, backends or structural events rather than rewrites.

Two things would make us stop and rethink rather than push on. If the compile pipeline can't rebuild a mid-sized dirty subgraph inside a frame, incremental recompile is the wrong shape and the live canvas is what gives — we'd fall back to edit-then-restart and say so plainly. And if index reduction on real coupled models proves harder than expected, we restrict the supported class to index-1 and reject the rest with an explanation, rather than shipping a solver that's subtly wrong on the models people most want to build.
