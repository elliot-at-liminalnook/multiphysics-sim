Planning doc — v0.6

A pluggable multi-domain physics simulator.

Rust and Bevy are settled. Everything below is a proposal, not a decision — select any block with the Redline controls and tell me what to change. We'll iterate on this page until the plan is right, then start building.

What we're building

A simulation core where each physics domain — rigid body, thermal, fluid, electrical, whatever comes later — is an independently authored plugin. Domains advance on their own terms and exchange quantities through a shared, explicit coupling layer rather than by reaching into each other.

The model itself is data, not code. Which components exist and how they're wired together is authored while the simulation runs — on a canvas, or from a script — and takes effect without a rebuild. Plugins ship the physics; you assemble the system live. This is the Modelica bargain, and it's the part worth stealing.

Bevy's ECS is the substrate: entities carry state components from any mix of domains, and the plugin system is already the extension point we need. Bevy's renderer gives us visualization for free, but the core should stay usable headless.

Detail on demand

The case worth designing for: a full circuit board solved honestly — extracted parasitics, hundreds of nodes, switching transients — and then handed to the rest of the system as a box with five ports. Both are the same board. The detailed model is the truth; the reduced one is what the enclosure, the fan, and the battery actually talk to.

Nothing about that is specific to boards. It's the general move: solve a subsystem at the resolution its physics demands, then expose a cheap surface that preserves whatever the outside world can observe. A gearbox, a battery pack, a hydraulic manifold — same shape.

  • Nanoseconds Traces and packages.

    An extracted RLC network with thousands of nodes. Where signal integrity and switching losses actually live.

  • Microseconds Functional blocks.

    Regulator, MCU, driver stage. Behavioral models with the transients averaged out but the control loops intact.

  • Milliseconds The board as one component.

    Power in, a handful of signal ports, one thermal port radiating total dissipation as a function of load.

  • Minutes The board in its enclosure.

    A heat source next to a fan curve and a chassis. Nothing at this level knows what a trace is.

Every rung is a legitimate model of the same object, and which one you want depends entirely on the question you're asking. So fidelity should be a runtime dial, not an architectural commitment.

A subsystem is just a component

A model containing a graph exposes ports exactly like a primitive does, and nothing outside can tell the difference. That one rule buys the whole hierarchy — boards nest in enclosures nest in vehicles, with no special case at any level.

Three ways to get the reduced model

Hand-authored surrogates, validated against the detailed run. Automatic order reduction — linearize around an operating point, then balanced truncation or moment matching, which is the well-trodden path for interconnect. Or fit a small state-space to simulation data. All three end at the same place: something that honors the port contract for less money.

Validity envelopes

A reduced model is only true somewhere — a frequency band, a load range, a temperature window. That envelope is declared as part of the model and checked while it runs, so leaving it is an event you can see rather than a wrong answer you can't.

Adaptive fidelity

You pay for detail only where you're looking. The board runs as an RLC network while you're debugging a gate driver and as a three-parameter thermal box while you're tuning the fan curve — swapped at runtime, with state handed across. Timescale separation is exactly what makes the coupled system tractable at all.

Zoom is a real operation

A reduced model keeps a link to what it was derived from, so opening the box on the canvas shows the network underneath — and changing that network marks the surrogate stale and offers to re-derive it. Provenance is what keeps the two from silently drifting apart.

Proposed architecture

Domain plugins

Each domain is a Bevy Plugin that registers its own components, resources, and systems into a shared fixed-timestep schedule. A domain declares what it reads and what it writes; nothing else is public.

Coupling layer

Cross-domain exchange goes through acausal connectors rather than hand-wired reads and writes — see below. Explicit, inspectable, and the only place where domains touch.

Solver scheduling

A fixed master timestep with per-domain substepping. Domains that need finer resolution subcycle internally; the coupling layer syncs at master-step boundaries.

Integrators as a library

Semi-implicit Euler, RK4, and friends live in the core as reusable pieces so each domain isn't reinventing time integration.

Modelica, but you can see it

The idea Modelica gets right is the acausal connector. A component declares ports; each port carries a potential variable and a flow variable. Wiring two ports together asserts two equations — potentials are equal, flows sum to zero — and nothing else. You never decide which side is input and which is output; the solver works that out from the assembled system.

That single rule is what makes multi-domain coupling uniform — every domain is the same shape, only the units change:

Mechanical

velocity · force

Electrical

voltage · current

Thermal

temperature · heat flow

Hydraulic

pressure · mass flow

A domain plugin's real job, then, is to define its connector kinds and ship components that constrain them. Coupling two domains is a component with one port of each kind — a pump bridges electrical and hydraulic, a resistor bridges electrical and thermal. No special cases in the core.

The graph is the source of truth

Components and connections live in a runtime graph, not in compiled code. Editing it is an ordinary mutation, so the visual canvas, a script, and a loaded model file are all just three ways of writing to the same structure.

Incremental recompile

Changing the graph re-runs the pipeline: flatten to an equation set, do the structural analysis, index-reduce the DAE, hand the result to the solver. Only the affected strongly-connected components get rebuilt, which is what makes editing-while-running feel instant instead of like a restart.

Visible by default

Where Modelica's tooling goes opaque, we stay legible: live values annotated on the wires, flow direction animated, residuals and solver iterations shown per component, and the flattened equations viewable for any node you select. Debugging a stiff model should be a matter of looking at it.

Scripting for what graphs are bad at

An embedded language covers the cases a canvas handles poorly — parameter sweeps, procedurally generated topologies, controllers, and test scenarios. Same API surface the editor uses: spawn, connect, set_param, step. Scripts can also define new component equations at runtime, which is how a user adds physics we never shipped.

Drive it like the real thing

The honest test isn't applying a torque to a shaft — it's wiring a real supply to a real bridge to a real motor under a real load, running a controller that doesn't know it's in a simulation, and then asking what the whole system did. The interesting assertions cross domains: volts in one, shaft speed in another, junction temperature in a third, all in a single statement about one run.

scenario "cold start under load" {
  supply.v      = 24
  load.torque   = ramp(0 → 0.4 N·m over 2 s)
  controller    = wasm("firmware/foc.wasm") @ 10 kHz

  expect motor.speed          reaches 3000 rpm within 250 ms
  expect motor.speed          settles within 2% of setpoint
  expect bridge.junction_temp stays below 85 °C
  expect supply.current       never exceeds 12 A for longer than 50 ms
}

Assertions are temporal, and about the system

Reaches-within, settles-to, stays-below, never-exceeds-for-longer-than. These are statements about a trajectory rather than a final value, and they name signals from any domain in the model. A failure reports the moment it happened and the surrounding trace, not a boolean.

A controller is just another subsystem

It has ports and it composes like anything else — the only difference is that it's causal. It reads sensor values and writes actuator commands, where the network around it is acausal. Both kinds of block coexist in one graph; the controller simply declares direction on its ports and the solver stops trying to infer it.

Any language, through WASM

Compile the block to WebAssembly and load it at runtime, and the language it was written in stops mattering. The real prize is running the actual firmware against the simulated plant — hardware-in-the-loop without the hardware, and a control bug that reproduces exactly on someone else's machine.

The re-entrancy problem

This is the part that needs care. An implicit solver evaluates a step several times while searching, and may reject a step and retry it — so a stateful controller called during those probes would advance its integral term four times for one millisecond of simulated time. Foreign blocks therefore need snapshot and restore, committing only on accepted steps. WASM makes that tractable: the entire block state is one linear memory, so a snapshot is a memcpy.

Rate, budget, and sandbox

A block runs at its own rate with explicit sample-and-hold, so a 10 kHz control loop sitting on a plant stepping at microseconds is an ordinary scheduling fact rather than a special case. Fuel limits keep a hung or hostile block from taking the simulation with it, and the sandbox means running someone else's firmware isn't a decision you have to think hard about.

Emergence as the acceptance test

The proof that a multi-domain core is rigorous isn't that a pendulum swings. It's that you change one value at one edge of the system and behavior nobody encoded falls out the other end — because the coupling was honest enough to produce it. So the acceptance suite should be a list of documented surprises, each with published numbers to fail against.

Every one of these has the same shape: a single parameter at a boundary, a qualitative change in what the whole system does, and a reference measurement from the literature.

mechanical

Kapitza's inverted pendulum

Shake the pivot up and down fast enough and the upright position becomes stable. Nudge the bob and it returns to vertical, standing on nothing.

Proves: integrator fidelity and timescale separation. The effect lives entirely in the averaged residual of a fast oscillation, so a step size that's merely adequate erases it completely.

mechanicalstructural

Huygens' coupled clocks

Two pendulum clocks on a shared flexible beam settle into exact anti-phase within the hour, whatever their starting positions. The beam moves by micrometers.

Proves: weak coupling survives our connector layer. All the information passes through a tiny amount of momentum exchange — round it away and the synchronization never appears.

electricalthermal

Current hogging

Two identical devices in parallel should split the load evenly. With a positive temperature coefficient they self-balance; flip that coefficient negative and the marginally hotter one draws more current, heats further, and takes all of it. Same topology, same parts — the sign of one derivative decides whether the board survives.

Proves: the electro-thermal loop closes in both directions — dissipation heats the part, temperature moves resistance — with no special case anywhere.

thermalacoustic

The Rijke tube

A heated gauze a quarter of the way up an open tube makes it sing. Steady heat in, a loud pure tone out, with no oscillator anywhere in the model. Slide the gauze past the midpoint and it falls silent.

Proves: Rayleigh's criterion emerges rather than being asserted — heat added in phase with the pressure wave feeds the mode. The position dependence makes it sharply falsifiable.

hydraulicstructural

Water hammer

Close a valve in a tenth of a second and pressure spikes to many times what the pump can deliver — routinely enough to split the pipe.

Proves: we're carrying compressibility and a finite wave speed. An incompressible network solve cannot produce this transient at all, and the Joukowsky prediction gives us an exact number to hit.

fluidstructural

Flutter

Below a critical airspeed the structure damps any disturbance. A few metres per second above it, the same structure starts extracting energy from the airflow and shakes itself apart. Nothing changed but one boundary value.

Proves: the system finds a stability boundary we never wrote down — the phase lag that inverts the sign of the damping is a consequence of the coupling, not a term in it.

Two things follow for the design. Integrators have to be good enough that these effects survive discretization, which argues for energy drift being a first-class diagnostic rather than something you discover later. And every scenario needs a stored reference trace, so a regression shows up as a number rather than as a simulation that looks a bit wrong.

Open questions

01

Which domain do we build first? The first one shapes the core's API more than any later one — and, given the section above, the better question may be which surprise we're chasing first.

My lean: rigid-body mechanics, because Kapitza and Huygens are single-domain and can therefore judge the core before any coupling exists. Then electrical and thermal as the first pair, since current hogging is the cheapest honest test of a two-way loop.

02

Which embedded language? Rhai is pure Rust and embeds without ceremony; Lua is faster and everyone already knows it; WASM lets people write components in any language at the cost of a much heavier boundary.

My lean: both, because these are two different jobs. Rhai for authoring — building models, sweeping parameters, writing scenarios — where you want a small language with native Rust types across the boundary. WASM for foreign subsystems that participate in the solve, where sandboxing and snapshot-restore matter more than ergonomics. Trying to make one language do both is what makes this question feel hard.

03

How strict do we get about units and dimensional analysis? Type-level units catch real bugs but cost ergonomics everywhere.

My lean: newtypes over f64 for the quantities that cross domain boundaries, plain floats inside a domain.

04

What's the intended use — an interactive sandbox, a batch solver you script and inspect afterward, or both?

My lean: headless core plus a Bevy app for visualization, so batch runs never depend on a window.

05

Determinism: do we need bit-reproducible runs across machines, or is run-to-run repeatability on one machine enough?

My lean: same-machine repeatability now, but avoid choices that foreclose full determinism later.

06

Do we reuse an existing physics crate (Rapier, Avian) for rigid body, or write our own so the coupling model is uniform across domains?

My lean: write our own simple solver first. Learning the domain API matters more early than physical fidelity.

07

Is every domain equation-based? Rigid-body contact and grid-based fluids don't flatten into a DAE the way a circuit does, so forcing them through one solver may be the wrong trade.

My lean: hybrid. The connector graph is the interface everyone honors, but a domain may solve however it likes internally and only reconcile its port equations at step boundaries.

08

What happens to state when you rewire a running model? Deleting a component mid-run leaves the solver holding values for equations that no longer exist.

My lean: preserve state for components that survive the edit, re-initialize only the affected subsystem, and offer a pause-on-structural-change toggle for when you want to be careful.

09

Do we import Modelica models, or define our own format? Compatibility buys an existing component library; a native format buys us years of not implementing a language spec.

My lean: native format, serialized straight from the graph. A partial Modelica importer is worth doing once we know our own semantics, not before.

10

Who produces the reduced models? Automatic order reduction is a deep specialty and only behaves for linear time-invariant subsystems; hand-authored surrogates work everywhere but rely on someone knowing the physics.

My lean: hand-authored surrogates plus a validation harness that runs both fidelities and reports divergence. Automatic reduction lands later, for the linear cases where it's actually sound.

What a surrogate actually is. For the board: a lumped RC network on the thermal port — junction-to-case resistance, case-to-ambient, one thermal mass — plus an efficiency curve on the power port. Five or six numbers standing in for a few hundred nodes. The skill is entirely in choosing that structure; nothing about it is laborious once chosen.

Where the numbers come from. The human picks the structure, an optimizer picks the constants — least squares against traces from the detailed run. That split is what makes "hand-authored" affordable: you supply physical judgment about which effects survive the reduction, not curve-fitting done by hand.

What the harness measures. Both fidelities run the same scenario under identical boundary conditions with every port recorded, and divergence comes back as numbers — peak error, RMS, and the moment it went worst — instead of two plots someone eyeballs. This is also the first real consumer of the determinism guarantee, since the comparison is only meaningful if both runs are reproducible.

Excitation is most of the difficulty. A surrogate matched at steady state can be wildly wrong on a transient, so the harness sweeps rather than spot-checks: step response, a frequency chirp, and the duty cycle you actually care about. Nearly every surrogate failure in practice is a model that was only ever checked at DC. The most realistic excitation available is the real one — drive the subsystem with its actual controller, as above, and compare fidelities under the load it will actually see.

The envelope falls out of the sweep. This is the part I like most — the region where divergence stays under threshold is the validity envelope from the next question. It stops being a promise someone wrote in a comment and becomes a measured artifact of the fit, re-derived every time either model changes.

What it costs to build. A scenario runner, a port-trace recorder, and a comparison report. Those same three pieces are what the phenomena above need in order to run as regressions, so this is shared infrastructure rather than a detour — which is most of why I'd start here rather than with the automatic path.

What unlocks automatic reduction later. Balanced truncation needs a linear state-space, so the precondition is a domain being able to emit its Jacobian around an operating point. Put that in the domain trait now, even unused, and automatic reduction becomes available for the linear subsystems without a redesign.

11

What happens when a model leaves its validity envelope mid-run — warn and keep going, clamp, or automatically escalate to the detailed model? Escalation means re-initializing state and changing the timestep underneath a running solve.

My lean: warn and record by default, with auto-escalation opt-in per model. Silent fidelity switches are how you stop trusting a simulator.

12

How far do we take error accounting? Per-model error is tractable; composing bounds across a hierarchy of surrogates is a research problem.

My lean: measure and surface per-model divergence against the detailed run, and make no claim about end-to-end bounds we can't back up.

13

How hard do we hold the line on conservation? Symplectic integrators keep energy bounded over long runs but constrain what else the domain can do; general-purpose implicit solvers are far more flexible and quietly bleed energy — which is precisely how a Kapitza pendulum falls over for reasons that aren't physics.

My lean: symplectic wherever the domain permits it, and energy drift reported per domain as a standing diagnostic, so when we do bleed we can at least see it happening.

14

Are assertions a small declarative form, or just code in the scripting language? Code is obviously more expressive, and obviously worse at explaining itself.

My lean: a declarative form. An assertion the runner can introspect can plot the signal it was about, mark the moment it broke, and say which term of a settling criterion failed. An arbitrary predicate can only return false. Escape hatch to a script for the rare thing the form can't say.

15

How real does a foreign controller's view of the world get? Real firmware reads a quantized ADC on a sampling clock, drives PWM with dead time, and responds to interrupts that arrive late.

My lean: model the peripheral boundary — sample rate, quantization, conversion delay, PWM granularity — because that is exactly where control bugs live, and skipping it makes the whole exercise decorative. Emulating the instruction set is a different project.

Build order

  • Core skeleton. Cargo workspace, Bevy app, fixed-timestep schedule, the Domain trait and plugin registration.
  • Connector algebra. Ports, potential/flow semantics, graph → flattened equations → solver, proven on a trivial domain like a resistor network.
  • First domain. One real solver end to end, with a scene it can run and a way to watch it — done when the Kapitza pendulum stands up on its own.
  • Second domain. The one that proves the abstraction — deliberately unlike the first, coupled to the first through a bridging component.
  • Hierarchy. Subsystems as components, one hand-authored surrogate beside its detailed model, and the harness that measures the gap between them.
  • Live canvas. Build, rewire, and inspect a running model without restarting it. Incremental recompile lands here.
  • Scripting. Embedded language over the same graph API, plus scenario files with whole-system assertions and enough diagnostics to trust the numbers.
  • Foreign subsystems. WASM blocks with snapshot and restore, peripheral-boundary modeling, and the motor scenario running end to end against a controller we didn't write.
