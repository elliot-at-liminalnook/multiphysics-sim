1. Orientation

The repository is a multiphysics simulator with one job around it: take a robot from a CAD model through a physics model, a controller and a test, to measured results and printed parts, in one Rust process. The rules that shape every part of it are in AGENTS.md. The three that explain most of what follows:

  • CAD owns the robot's physical definition. Masses, joints, motors, materials and limits come from the CAD file with their provenance. The simulator never fills in a missing value quietly; it lists every guess as an assumption and says whether it blocks evidence.
  • Everything runs in Rust, in the viewer's process. Simulation, CAD geometry, the user interface and hardware driving all live in one binary, sim-spatial. There is no server the viewer depends on. The browser and the Python/C controller clients are compatibility surfaces, not the architecture.
  • One execution path. Interactive viewing, headless runs, tests and learning share the same runtime and the same observation and action contract. Seeds and inputs are recorded so any run can be replayed.

Reading the code from the bottom up, there are five layers. Each one depends only on the ones below it.

The layers also give a reading order. Sections 2–4 cover the physics and how it is composed. Section 5 covers the viewer. Sections 6 and 7 follow a robot from CAD to the hardware bench. Sections 8–10 cover what is built on top: evaluation and learning, content, and tooling. Section 11 is the status table, and section 12 suggests where to start reading.

2. Elements and equations

A model is a set of elements joined at ports. An element is a Rust type implementing Behavior: it declares its states and, every solver iteration, writes a residual. A port carries an across quantity and a through quantity in the power-conjugate pairs of each domain: temperature and heat flow, voltage and current, angle and torque, pressure and volume flow. Connecting ports makes a node; the compiler adds one equation per node lane saying the through contributions sum to zero.

Two things the domains share. Every element can report energy and entropy production, and the runtime checks the second law at every commit (second_law_tolerance in Runtime). And every element may provide a jacobian of its own; those that do not get finite differences on their own inputs only, so the Jacobian of a whole island is assembled element by element rather than by differencing the whole system.

3. Compiling and solving

A ModelWorld is a description. Running it takes three steps, in three crates.

Compile (sim-compile). The connection graph is validated (port kinds, units, one owner per frame, no dangling through lanes) and split into islands: connected components that share no unknown. Each island gets one unknown vector and one residual vector in a fixed layout. Every unknown is registered as a named state in model.state, which is how the viewer, recordings and tests address values later.

Integrate (sim-dynamics). A Simulation owns one island as a System (anything that can say how far a (state, rate) pair is from satisfying its equations), an integrator, the state and a trace. Three integrators exist and the choice is deliberate:

Solve (sim-solve). Each implicit step is a Newton solve with a line search over the island's residual. The Jacobian is sparse and coloured, so one residual evaluation fills many columns. Its LU factorisation (from faer, with the symbolic analysis shared by sparsity pattern) is kept across iterations and steps for as long as the residual keeps halving: the modified Newton method. The same crate holds constrained solvers (dogleg, augmented Lagrangian, barrier, least squares). Behind Cargo features it also holds the search tools the learning code uses: Bayesian optimisation (bayesian), CMA-ES (evolution), a conic solver (conic, Clarabel) and an IPOPT binding loaded at run time (native-ipopt).

The Runtime in sim-compile ties the three together and adds what every host needs: a committed, consistent state after each step; checkpoints; adaptive stepping with retries that never cross a controller tick; and the block scheduler of section 4.

4. Composition: systems, blocks, robots

Hand-built ModelWorlds are for tests. Everything a person or an agent builds goes through a system file, *.system.json (schema sim.system/2, crate sim-system). A system file is a hierarchy of definitions; each definition has instances, nets joining their ports, boundary ports, parameters, and display-only placement. It also carries the numerical settings it was validated with, saved studies, a realtime profile and acceptance tests, so a file alone reproduces its runs.

Three pieces of machinery sit on the document:

  • Commands (sim_system::Command): the one edit set, applied atomically with validation, used identically by the viewer's controls, REST and the CLI. The store keeps a shared undo journal beside the file.
  • Resolve: port typing through the hierarchy, net checks (a signal net has one output; a block's signal joins only its exact quantity; physical ports must share a connector), and review findings for things that are valid but incomplete.
  • Flatten: the hierarchy becomes one ModelWorld with path identities (rover/left drive.unit), which is what section 3 compiles. Generators run here.

Blocks: controllers that run only at committed ticks

A controller is not an equation. It runs at discrete instants, keeps state, and may be code the simulator cannot see inside. So a block is a separate kind: a shadow element holds its outputs as states the plant can read, and a scheduler in the runtime runs the block's implementation between island advances. The rules (full text in docs/architecture/composition.md):

A block does not tie the islands it touches together. Its inputs are sampled from committed state and its outputs are constant between ticks, so island grouping ignores the connections to a block's shadow element: two rooms, each with its own thermostat block, compile to two islands and still step in parallel (a_block_does_not_merge_the_islands_it_reads_and_drives in sim-phenomena/tests/blocks.rs). A block input may be declared a setpoint (BlockPort.setpoint, or an FMU input annotated sim.setpoint); left unconnected it holds its start value instead of being a dangling port, and teleoperation can drive it (section 6). These changes are written and their own tests pass, but five phenomena scenarios started failing with them, three of which run a controller as a block (section 8); the cause has not been found.

Two families of implementation exist: couplers and FMUs.

Couplers: Rust, Rhai, Python and C

A coupler is the older and simpler seam: one call per sample instant, sensors in and actuator commands out, in lockstep with the simulation. CouplerBlock adapts any coupler to the block trait, so all of these run on the same scheduler: a Rust closure, a Rhai script, and an out-of-process program speaking the newline-delimited JSON frame protocol of sim-couple (the Python and C clients in clients/).

Rhai is the scripting language the project uses for controllers, lesson cues and experiment recipes (sim-script). A Rhai controller is a single control function. RhaiController::sample turns the contract's arrays into named maps, calls the function, and refuses a reply whose command names do not match the contract exactly. FMUs

An FmuBlock (sim-fmi) loads an FMI 3.0 Co-Simulation FMU. The archive is checked against a stated profile before any binary is loaded. Units must match exactly (SI exponents, no conversion). Each block gets its own instance, its parameters are set from the system file, and the FMU's state goes into runtime checkpoints when the FMU can serialise it. Everything outside the profile is refused by name: FMI 1 and 2, Model Exchange, Scheduled Execution, clocks, arrays, strings, event mode, or a missing binary for this platform. The crate has its own hand-written ABI over libloading. The existing fmi crate was rejected because its strict schema cannot hold the unit attribute that common tools write.

Robots as assemblies

A robot is not a special runtime. sim-domain-robot holds robot.articulated, one element for the whole mechanism: a floating or grounded base, tree joints in minimal coordinates, loop closures, optional modal flexibility per link, and contact from the links' own geometry. Its equations are inverse dynamics in residual form: a forward pass for poses and twists, a backward Newton–Euler pass for the force each joint transmits, each joint port absorbing the torque its motion demands. Around it, sim_runtime::physical::assemble builds, per motor, the chain battery → bridge → motor → gearbox → joint, with winding and case thermal paths, servo firmware, encoders and an IMU, all from registry elements.

In a system file the robot is a Generated instance. The generator runs the same assemble and exposes a boundary: supply_p/supply_n (the motor bus), ambient (where windings and mounts shed heat), <joint>.target inputs, and <joint>.angle, .speed and imu.* outputs. A battery, an enclosure and controller FMUs are ordinary parts wired to those ports.

A robot travels with its model world. Element factories take scalar parameters only, so the articulated element names its PhysicalModel by a key: the first 52 bits of the BLAKE3 hash of the model's JSON, an integer an f64 holds exactly. The text itself is kept in ModelWorld.resources, and compiling installs it into a process cache that the factory reads (crates/sim-core/src/resources.rs; a different text with a colliding key is refused). So a flattened system serialises, rebuilds in another process and runs the same (a_flattened_robot_system_serialises_and_runs_the_same).

5. The native viewer

sim-spatial is the one application (Bevy 0.19.1; 156k lines, the largest crate). Every workflow is a mode of the same window, and the user switches between them in the window. A mode is a Bevy state; the computed states ModeScope and SpatialScreen follow it. Launch flags, or a bare path, choose the first mode: sim-spatial robot.system.json opens Build mode, *.simrobot.json Robot mode, a place.json directory Place mode, a lessons directory Lessons mode, *.rcad CAD mode.

Four shared services keep the modes from duplicating each other (docs/architecture/native-viewer.md is the design record, kept current with each change):

  • Actions. Each mode has one action type. A REST command, a toolbar button, a key and a REST batch all produce the same action, and one handler applies it. The capability list is generated from the action registry, so the REST surface cannot drift from the UI.
  • Jobs. Nothing outside jobs/ starts a thread or a process; a test scans the source tree to enforce it. One-shot jobs run on an I/O, compute or dedicated pool with cancellation and progress; long-lived workers (a simulation run, a playback clock) are named threads with a command channel in and a generation-stamped snapshot out.
  • Documents, selection, annotations. One document registry, one selection every mode reads, one annotation service with one thread panel (sim-annotate); comment threads behave the same in CAD, Build, Inspect, Lessons and Robot.
  • UI kit and camera. Tokens, buttons and docks come from ui_kit; the shared camera has 13 REST commands tagged with every orbit mode.

The REST server (sim-api) is loopback-only and bounded: POST /v1/batch queues ordered commands, GET /v1/jobs/{id} polls them, GET /v1/capabilities lists them, published resources (/v1/system_state, /v1/project_state, …) and /v1/events/… give long waits a non-blocking path, /v1/images/{id}.png serves renders. Transport threads never touch application state; the viewer polls one command at a time from its own update loop. The same server runs --headless, with the window-only commands refused.

6. The robot pipeline

A robot project (*.robot.json, sim_runtime::robot_project) carries one robot through five steps, each a mode of the viewer and each reachable over REST. The project file holds what is not the robot's physical definition: the description the person gave, the acceptance test, the design conversation, and where results, lessons and parts go. The robot itself is the CAD file.

Design: CAD in process

RoboCAD, the Python and OCCT CAD application in cad/robocad (30k lines), is now only the reference for how things should behave. Its Rust port, sim-cad, owns the .rcad archive format: it keeps every original byte and entry, and it identifies a model by the SHA-256 of the file. It reaches the OCCT kernel through a narrow C ABI over a C++ bridge of about 1,100 lines (crates/sim-cad/native), linked to OCCT 7.7.2. The choice of a hand-written bridge over a general wrapper is recorded in crates/sim-cad/README.md. The bridge covers primitives, transforms, booleans, fillets, chamfers, extrusions, plane sections and face and edge listings. Exact mass properties, sketches, references and saved views are written in Rust.

CAD mode in the viewer runs RoboCAD's operations under their original names and argument binding. sim_cad::ops::run has 84 match arms covering 94 operation names. Every operation is one undo step. A design assistant (sim-agent, a Codex conversation) edits through the same commands. The viewer never starts, calls or waits for RoboCAD.

On 8 October the rest of the migration was written (plan and limits: docs/cad-migration-and-composition-plan.md). Every feature that used to refuse by name now runs in process:

  • Mesh import (STL, OBJ, PLY, 3MF) with RoboCAD's unit guess, and print checks (wall thickness, export validation, overhangs): sim_cad::printing.
  • Print studies: splitting a part for printing (cut planes with dowel, insert and dovetail joints), strength, whole-or-split, plans with plates written as 3MF, assembly guides and coupon kits (sim_cad::print, with the stress check and planner in sim_runtime::print_tools, which the sim-print binary now wraps). They run as viewer jobs; a job that changes the document publishes one undo step when it ends, refused if the document changed meanwhile.
  • Experiments on the export, captured review, comparisons and evidence threads, candidates as staged edit batches accepted as one undo step, identification applied through the actuator registry (sim_cad::experiments).
  • Model scripts in Rhai over the shared operations, sketches and GT2 belts (sim_cad::scripts, cad_script); the turntable's scripts are .rhai now and their Python is gone.
  • Components and assemblies: definitions, parameters, occurrences, regeneration and composition edits (sim_cad::component_edit, sim_cad::component_graph), and reference poses with motion patterns (sim_cad::pose).

Each has tests in sim-cad (52 tests, all passing on 9 October). What has not happened yet is the plan's last step: a REST walkthrough of each feature in the live viewer. The agent's view of the editor is its guide command, which states the contract plainly:

The RoboCAD client is gone: sim_runtime::cad_client (7,500 lines) and the CAD parity harness (cad_parity, which ran the Python and Rust implementations side by side) were deleted, CadDocument has no client, attach field or child-process slot, and a recent-documents entry that pointed at a RoboCAD URL is listed disabled and refused by name. docs/cad-parity-harness.md is kept as the record of what the harness compared. Two stale notes remain: the Cad mode's doc comment in app/mod.rs still says documents are edited through RoboCAD, and crates/sim-cad/README.md still opens with "Source reviewed, unexecuted". The ledger of what is ported is docs/cad-rust-physical-derivations.md.

Model: the physical export

sim_cad::physical::export turns the archive into the simrobot v4 model in process: links from bodies merged by fixed joints and motor mounts, with exact B-rep mass and inertia combined by the parallel-axis theorem; joints with bearing physics estimated from the motor shaft or a printed pin unless set in CAD; library motors with their electrical, gearbox, thermal, firmware and driver blocks; sensors, cables, battery, materials. Every guess is listed in source.assumptions with whether it blocks evidence and how to resolve it. Three things are declared not modelled: flexible links (every link is rigid), link-to-link contact, and bearing inference from cylinder pairs.

Test: the robot as composed

The test runs the project's own system file (<name>.system.json): the model as a generated robot, at first alone with the supply and ambient its model defines, and with whatever controller FMUs, battery or thermal parts were added to it in Build mode. It runs on the same path as any system: flatten with the generators, compile, bind blocks, schedule. Controller blocks are never substituted. The test's trajectory drives only inputs the system leaves open, through a test-bench block on the same scheduler at the model's control period and latency.

Evidence is bound to what ran. A report carries a fingerprint (the system's physics hash, the SHA-256 of every file read, the run settings, the test); the project's status compares it with what a run would be now and reports current, or stale with what changed. A stale pass neither completes the Test step nor allows Make. The same fingerprint type serves system tests in Build mode (system_evidence).

Learn and Make

Lessons for the robot are written by the AI from its numbers and a render (section 9). Make writes every printed body as a binary STL under make/ with a manifest naming the tested CAD revision, each part's material, mass and print settings (unstated settings named as assumed). Printed-part strength is judged after a test by sim-print's layer-aware voxel stress check, with loads from the run's peak motor torques and joint reactions and filament values from the print registry.

7. Hardware

The bench is a printed leg of HiWonder HX-30HM serial bus servos (knee, worm and belt-driven hip, IDs 1–3) and a nine-servo chain (IDs 4–12). Between the host and the servos sits a Sipeed Tang Primer 25K FPGA, and the design rule from AGENTS.md is that its safety holds whatever the host does. The chain uses the FPGA's bench profile; the leg uses its calibration profile, which adds taught travel windows. The FPGA sources live in the separate sipeed-tang-primer-25k repository; this repository holds the host side, a frozen source snapshot with its validation report (examples/actuators/hx30hm/software-validation), and an ESP32 host that now drives the leg over Wi-Fi.

On the host, sim_runtime::hardware holds two application services with no transport of their own: calibration (serialised acquisition, taught poses, sweeps, tuning, durable records, an independently reachable STOP and motion leases) and bench (gait playback on the leg, live references, FPGA plans and receipts). Two browser pages predate the native front end and still work: the motor bench (serve_motor_bench, FPGA gait playback) and the calibration page with its viewer mirror (serve_actuator_calibration). Both are thin HTTP adapters over the same services. The native viewer's hardware front end (Robot mode's hardware panel, the leg clock aligned with the simulation, Sim/Leg/Both playback) is written and source-reviewed, but docs/hardware-checklist.md is explicit that its checklist items HW-01 to HW-11 have not been executed on the leg since the last changes; the browser page remains the reference until a pass runs.

The measurement side feeds the simulator back. The actuator registry (actuator_registry, sim-actuator-profiles) is the one source of accepted motor families, promoted from identification captures and flowing to CAD, simulation, screens and hardware limits; nothing is hand-copied. A staged characterisation campaign (stages A–K: breakaway, gain, speed, stopping distance, thermal) is implemented and tested against a simulated rig, with a hardware rig written for the bus; it has not yet run on the leg.

The ESP32 host and the leg

The ESP32-P4 host (firmware/robot-link) has been running on the leg's bench since 8 October. It replaces the dock's USB chip with a UART on the FPGA's G7/G8 pins and joins the bench's Wi-Fi network. The FPGA's calibration image with those pins is written to the dock's SPI flash, so it boots without a host (receipts in examples/actuators/hx30hm/hardware/2026-10-08-robot-link). The board's Wi-Fi goes through its C6 co-processor, and esp_hosted is pinned to the C6's 2.12 line: with 3.0.9 the data path died within a minute. The firmware's portable C core (core/) runs one transaction at a time, keeps armed motors' telemetry fresh, sends lease heartbeats only while a page session is alive, and is tested two ways: make -C test against a behavioural model of the supervisor, and make -C cosim against the real Verilog under Verilator with UART bits at the real baud rates, built once for each profile.

The leg can be driven two ways through it. A raw TCP tunnel (port 4196, bridged to a pty by tools/tunnel_pty.py) lends the UART to the Rust calibration panel, which calibrated the leg over Wi-Fi. The board's own page does the rest. Its state, STOP, gait selection, turn confirmation and teaching are also REST commands; arming, jogging and playing need the page's live session, which is what a lease is renewed from:

  • Arming, jogging and teaching. Arm sends the motor's taught window, anchored at its reading, then puts it in open-loop PWM mode for hold-to-move. A motor found outside its travel is armed with the window stretched only to where it already is, so it can come back in and no further out, and a held jog is zeroed at the window's edge. Poses are set where the motor is, named as in the panel (lower and upper), kept in the board's flash, and promoted into calibration.json by leg_gait_pack --pull-calibration, which keeps the previous file and asks for a reason when a travel widens.
  • The worm's turns. The worm's travel is 1.1 encoder turns, so a reading alone does not say where it is. The page draws the leg at each place the reading allows and the operator picks the one that matches; the count is forgotten on anything that could hide a turn (a missed reading, a half-turn jump, a gap, the tunnel taking the link).
  • Gaits. A gait pack built on the Mac (sim_runtime::hardware::calibration::gait_pack, from the same gait catalog, calibration, registry limits and CAD as the panel) holds each gait's desired reference and governor, a check sequence from the Rust governor that the C port must match, and the leg figure: the CAD collision meshes with per-link transforms, checked against the kinematic mirror to 0.08 mm, which the page draws for the preview, the live leg and the worm's places. Knee and hip play as servo position goals; the worm plays in servo speed mode with a position trim, because position mode cannot leave one turn.

On the leg so far (9 October): the link, the tunnel calibration, arming, recovering the knee from outside its travel, jogging, teaching poses and confirming the worm's turn have all been used. Not yet: a gait played on the leg, the worm's servo speed mode on this servo (its units are assumed to be counts per second), and a cold power-cycle of the dock to confirm it boots the flash image.

8. Evaluation and learning

Everything in this section runs on the sessions of section 5; none of it has physics of its own.

The phenomena suite

sim-phenomena is the acceptance suite for the physics: 35 scenarios, each a model of registered elements that must reproduce a published number, and must lose the effect when its falsifier is applied (for Huygens' clocks: make the beam rigid, and the clocks must drift apart). Huygens' clocks synchronise, the tippe top inverts, the passive walker walks, Chua's circuit goes chaotic, a Rijke tube sings, a silo shows Janssen's saturation, a sampled controller hunts at the wrong rate. The same model builders drive the exhibits in Phenomena mode.

Robot evaluation

Robot work goes through Session (host-independent episodes: inputs in, snapshots out, Rhai or an out-of-process controller inside) and EmbeddedEnvironment (sampled environments over the same runtime, actions as held controller inputs). On top of those: reproducible motion experiments with checkpoints; matched-input fidelity comparisons between the detailed model and a realtime profile; a controller leaderboard that ranks only measured, gated evidence; a gait lab that evaluates readable gait files; PPO training and a distilled "student" policy; contact-aware motion planning with several solvers (IPOPT, conic, Bayesian, CMA-ES, behind features). The browser's WASD walking and the native experiments share these exactly.

The state of the walking work is honest and mixed. The CAD-derived quadruped walks in the browser: it was observed at about 0.14 m/s under the robot-measured-400hz-reuse preset on 22 September. The leaderboard's recipes meet none of their declared gates (sustained heading, numerical agreement, realtime). The faster development gait is labelled experimental. examples/full-robot (355 entries) holds the experiments, their recipes and result sheets.

9. Lessons, library and the other content

Lessons

A lesson is a folder with a lesson.md: Markdown with YAML front matter and fenced blocks that embed live content. Three kinds carry systems: sim-scene (a system run, recorded and animated), sim-component (a library card) and sim-compare (a saved study). The others teach: sim-quiz, sim-recall, sim-reflect, sim-equation, sim-remedy, sim-task, sim-lab and sim-measured. sim-lesson parses and validates the file and reports errors as lesson.md:line. sim_runtime::lesson resolves the systems, records each scene on the same SystemSession the viewer uses, and checks every expect claim against the recording. A workspace test (crates/sim-runtime/tests/lessons.rs) runs that check over every lesson in CI. There are 27 lessons, among them gear ratio, backlash, battery sag, PID on a joint, worm self-locking and one built on a measured knee servo. They come with quizzes, recall prompts, sliders that re-record a scene, progress tracking and narration.

The library

library/ is content with one source each: 31 equation parts (*.part, hot-reloaded), 110 generated datasheets, 21 saved systems, the print registry (printers, filaments, printed-joint values; estimated values replaced only by measured coupons through sim-print promote), and 3D models for the viewer. library/CATALOG.md is generated from the registry descriptors.

Vision and places

sim-vision models the Raspberry Pi Camera Module 3 Wide as a pinhole camera with rolling shutter and exposure, renders deterministic frames of a described scene, and reconstructs depth by plane-sweep stereo with poses that come from the simulated mechanism (a camera turntable driven by an HX-30HM, examples/camera-turntable, CAD-derived). sim-place fuses scans into a place model with twelve query tools that serve a CLI and an MCP server, so an AI can look around a scanned room; Place mode flies through it. The finding that shaped the design: the servo's angle (0.004°) is a better pose than image refinement can give, and a smooth once-per-turn angle error is unobservable from neighbouring shots. The real cameras run from the stereo-camera project on the same ESP32-P4 board; the simulator side has not yet consumed a real scan.

Controllers in other languages

The seam protocol of sim-couple lets a controller run in another process, in any language. The protocol is newline-delimited JSON in lockstep, and the simulation speaks first:

A Python client that needs only the standard library (clients/python, simloop) and a C client (clients/c) implement it. Under the project rules these are compatibility surfaces: new controllers are written in Rust or Rhai, or arrive as FMUs.

Agents

The rule in AGENTS.md is that every screen can be used by an AI. In practice, every mode's commands appear in GET /v1/capabilities with a working example, and most modes publish a state resource (system_state, cad_state, robot_state, project_state, lesson_state, phenomena_state). Every mode also has a guide command that tells an agent starting cold where to begin: inspect_guide, system_guide (Build), lesson_guide, robot_guide, place_guide, cad_guide and phenomena_guide, plus project_guide for robot projects across modes. A test (every_mode_has_a_guide_of_its_own) fails if a mode is added without one.

tools/claude-pair runs two Claude Code roles through a local coordinator that runs the checks itself. An orchestrator writes bounded assignments and a worker implements them, with an optional director above both. Much of the viewer's migration ledger in docs/architecture/native-viewer.md was produced this way. That is why it reads as a sequence of accepted batches, each with an explicit "by reading, unexecuted" caveat.

Tests and CI

The workspace has 2,526 #[test] functions and 190 integration test files, and eight GitHub workflows: simulation, CAD, browser, experiment, walking reference, and one for each optional solver feature (Bayesian, conic, native IPOPT). The tests follow the project rules. The equation crates check analytic cases and conservation. Scheduler, FMI and composition semantics are tested in sim-phenomena/tests/blocks.rs, sim-fmi/tests and sim-runtime/tests/{composition,robot_acceptance}.rs. Parity tests compare native and WebAssembly builds. Source-scanning tests enforce the viewer's structure: threads and processes are started only in jobs, no window text tells a person to use REST, and commands keep their order.

Run for this map on 9 October, on the working tree: sim-core and sim-system (42 tests), sim-compile (26), sim-fmi (14), sim-cad (52), the block semantics in sim-phenomena/tests/blocks.rs (20), sim-domain-robot (200) and the viewer's library tests (874, 7 ignored) all pass, and the viewer's binaries build. The viewer's eight known failures of 8 October (CAD service-switching tests, two calibration-study timing tests, the copy guard and the source-size limit) no longer fail. sim-runtime passes 695 and fails 11, none of them new: nine hardware-bench UART mock tests, request_mirror_matches_the_server (it looks for struct Request in the example server, but the struct moved into hardware::calibration), and coreless_motor_loads_with_notes_snaps_and_heats in tests/authored_parts.rs. The firmware's make -C test and both co-simulation builds pass. The phenomena suite is the regression to look at first (section 8).

Two practical notes for anyone building: target/ grows past 100 GB, so build with CARGO_INCREMENTAL=0 and never a second target directory; and a workspace check takes minutes while the viewer crate takes much longer, so test the library crates first.
